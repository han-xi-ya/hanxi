# Hanxi 插件化决策与产品演进专项分析

> **文档状态**：产品与架构演进专题基线  
> **更新日期**：2026-09-18  
> **当前代码基线**：41 个静态注册的内建模块，其中 25 个为第三方工具托管模块  
> **结论摘要**：Hanxi 当前不是开放插件平台；近期重点是收束内部契约与共享托管能力，满足明确前置条件后再分阶段引入声明式扩展和受控子进程插件。

本文专门回答 Hanxi 是否、何时以及如何插件化，并描述产品从“模块化工具工作台”走向“可信 Windows 工具控制平面”的演进路径。当前实现事实仍以 `ARCHITECTURE.md` 为准，整体战略取舍仍以 `PROJECT_STRATEGY.md` 为准。

---

## 1. 当前结论

### 1.1 当前形态

Hanxi 当前的准确形态是：

> **模块化单体 + 静态 Wails Service 注册 + 模块运行资源按需激活 + 第三方工具托管。**

当前代码中的 41 个模块均在 `internal/app/app.go` 的 Composition Root 中构造并注册，模块级别均为 `LevelBuiltin`。前端视图可以异步加载，模块可以启停并执行 `OnInit()` / `OnDestroy()`，但这些能力属于单体内部的生命周期管理，不等于开放插件运行时。

`internal/extapi.Module` 当前只包含：

- `Info()`：模块元信息；
- `Nav()`：导航条目；
- `Services()`：静态注册的 Wails Service；
- `OnInit(context.Context)`：按需分配运行资源；
- `OnDestroy()`：释放模块资源；
- `IsInitialized()`：报告运行资源是否已初始化。

`LevelExternal`、`Permission` 类型及常量仍是未来扩展预留。`Permissions()` 和 `Protocol()` 已不在当前 `Module` 接口中；当前也没有插件安装、动态服务注册、协议握手、签名校验、能力授权、兼容性协商或第三方 UI 装载机制。

### 1.2 当前为什么不是开放插件平台

开放插件平台至少要求宿主能够对未知扩展完成发现、验证、安装、授权、启动、通信、升级、隔离、撤回和兼容性治理。Hanxi 当前不具备这些完整能力：

1. 模块与 Wails Service 在进程启动时静态注册，不能从目录动态增加未知服务；
2. 模块前端视图由 Hanxi 源码显式映射，不支持第三方任意 UI 包；
3. `Permission` 只是保留类型，不是当前内建模块调用路径上的强制权限边界；
4. `LevelExternal` 没有对应的 manifest 发现器、子进程管理器和通信实现；
5. 没有插件签名、来源信任、恶意版本撤回和协议兼容策略；
6. JobObject 能治理进程生命周期，但不是恶意代码沙箱；
7. 禁用内建模块不会移除已经注册的 RPC 路由，不能等同于卸载插件。

因此，对外表述应使用“模块化工作台”“内建模块”“托管工具”，不应使用“开放插件市场”“任意第三方插件”或“安全沙箱”等尚未成立的承诺。

## 2. 为什么现在不应直接开放代码插件

插件化不是把 `Module` 接口导出，也不是扫描一个目录后启动 EXE。过早开放会把尚未稳定的内部实现变成长期兼容负担。

### 2.1 当前优先矛盾

41 个模块已经证明 Hanxi 能覆盖多类 Windows 工具与工作流，但也暴露出比“扩展数量”更优先的问题：

- 托管模块仍存在下载、验证、安装、版本和实例治理的重复实现；
- 内部生命周期、错误、事件和状态契约尚未完全统一；
- 模块启用状态与静态 RPC 暴露之间还缺少统一调用门；
- 能力声明尚未形成宿主强制执行的授权网关；
- 扩展来源、签名、撤回、兼容和事故响应制度尚未建立；
- 用户更需要全局运行中心、更新中心和任务可观测性，而不是更多安装入口。

如果现在开放代码插件，宿主将被迫同时维护内部模块差异和外部协议兼容，问题会从重复代码升级为不可撤回的生态契约。

### 2.2 正确顺序

正确顺序是：

1. 先稳定单体内部模块契约；
2. 再把第三方工具托管的共性能力收敛为宿主能力；
3. 然后开放不执行任意代码的声明式工具扩展；
4. 只有声明式能力确实无法覆盖的需求达到规模后，才设计受控子进程插件；
5. 任意进程内插件、DLL 注入或 Go Plugin 不进入可预见路线。

## 3. 何时插件化

插件化应由可验证条件触发，而不是由模块数量或宣传需求触发。

### 3.1 可以启动声明式扩展的条件

以下条件应同时满足：

- ArtifactManager 与 ProcessSupervisor 等共享托管内核已经稳定，并被多数托管模块复用；
- 下载、校验、解压、安装、回滚、启动、探测、唤窗和退出均有统一宿主实现；
- 模块启用状态、生命周期和操作状态有唯一权威来源；
- 所有业务入口经过统一调用门，禁用模块不能绕过宿主继续执行；
- 工具来源、验证等级、许可证和网络行为可以被 manifest 完整表达；
- 至少完成两个正式版本的内部契约兼容验证；
- 已出现持续、真实、可复用的外部扩展需求，而不是只为减少一次编译。

满足后，可以先开放“声明式 Tool Manifest”：扩展只描述工具，所有下载、安装、运行与 UI 均由宿主提供，不执行扩展方代码。

### 3.2 可以启动子进程代码插件设计的条件

除满足上述条件外，还必须具备：

- 至少三个经过评审、确实无法由声明式模型表达的真实需求；
- 稳定且版本化的 JSON-RPC 或等价协议，包含握手、超时、取消、错误和事件语义；
- 宿主强制的能力授权，插件只能通过受控 Host API 使用敏感能力；
- 独立进程、JobObject 生命周期治理、崩溃隔离、资源限额和健康检查；
- 插件包签名、发布者身份、可信目录、撤回名单和降级策略；
- 安装、升级和回滚事务，不允许失败升级破坏已有可用版本；
- 明确的协议支持周期、弃用窗口和兼容测试矩阵；
- 维护者有能力持续处理供应链事件与第三方兼容问题。

任何一项缺失，都不应向第三方承诺代码插件生态。

### 3.3 不采用的形态

以下方案不建议采用：

- **Go `plugin`**：Windows 支持、构建一致性、版本耦合和崩溃隔离均不适合 Hanxi；
- **进程内 DLL 插件**：未知代码与宿主同权限、同地址空间运行，故障和安全边界不可接受；
- **任意 WebView UI 包**：会引入依赖、CSP、资源访问、设计一致性和持久兼容负担；
- **仅靠 JobObject 的“沙箱插件”**：JobObject 解决进程树和退出治理，不限制文件、注册表、网络或同用户权限；
- **无签名插件目录**：不能建立发布者身份、升级信任和事故撤回能力。

## 4. 哪些能力可以拆，哪些不应拆

“可拆”不等于“现在就拆”。判断标准是边界是否稳定、数据是否可序列化、失败是否可隔离，以及拆分后是否减少宿主维护成本。

### 4.1 第一批：适合声明式拆分的托管工具

25 个第三方工具托管模块是最适合演进为声明式适配的候选集合。其共性是 Hanxi 主要负责：

- 上游版本发现与资产筛选；
- 下载、完整性验证和安全解压；
- 安装布局与活动版本；
- 进程启动、就绪探测、外部实例识别、唤窗和退出；
- 跟随退出、桌面快捷方式、卸载和回滚；
- 统一控制台与状态展示。

其中，标准便携压缩包、单文件 EXE、稳定 GitHub Release、进程探测清晰且无复杂业务 UI 的工具，应优先验证 manifest 表达能力。它们不是立即从仓库删除，而是先把差异压缩为数据和小型宿主适配器。

带有 MSI、MSIX/Appx、AppInstaller、静默安装器、命名互斥体、命令通道或多形态安装探测的工具仍可逐步声明化，但需要宿主先把这些机制实现为经过审计的内建策略，不能允许 manifest 注入任意命令行或脚本。

### 4.2 第二批：适合受控子进程扩展的能力

未来只有以下类型可能需要代码插件：

- 需要解析专有协议或持续流式数据，但不需要直接嵌入宿主进程；
- 需要连接独立设备、服务或本地工具，并能通过结构化消息交互；
- 算法型任务，输入输出可序列化、可取消、可限时；
- 上游变化频繁，独立发布适配器明显优于等待 Hanxi 主版本发布。

这类插件也应把 UI 限制在宿主提供的表单、表格、日志、进度、操作和通知组件内。插件提供 schema 与数据，宿主负责渲染，避免形成不可治理的微前端生态。

### 4.3 应继续内建的能力

以下能力构成 Hanxi 的控制平面和信任根，不应交给第三方插件替换：

- 模块目录、生命周期状态机和调用门；
- ArtifactManager、ProcessSupervisor 与 Operation Center；
- DPAPI Secret Store、日志脱敏和配置迁移；
- JobObject、进程指纹、UAC、注册表、IP Helper、Appx 等 Windows 平台原语；
- 插件验证、签名、安装、授权、升级、撤回与兼容管理；
- 全局导航、运行中心、更新中心、通知和诊断导出；
- 权限决策与 Host API；
- 涉及系统级破坏性操作的最终复核与用户确认。

### 4.4 需谨慎评估的自建业务模块

frpc、文件快传、微信接入、Memo、消息板、OCR、端口查杀、局域网与系统诊断等模块包含较强业务语义、跨模块协同或敏感能力。它们可以先在单体内通过接口解耦，但不应为了“插件率”强行外置。

只有当某模块满足以下条件时才值得物理拆分：

- 发布节奏与主程序明显不同；
- 独立故障隔离有实际价值；
- 宿主接口稳定且数据边界清晰；
- 拆分不要求把敏感系统权限直接交给插件；
- 独立维护成本低于继续内建的成本。

## 5. 分阶段演进路线

### 阶段 A：内部模块契约做实

目标不是增加插件能力，而是让 41 个内建模块遵守同一套可验证规则。

主要工作：

- 以 Registry 为唯一生命周期状态源；
- 为业务调用建立 Enabled/Acquire/Operation 统一入口；
- 统一初始化、停用、取消、超时和退出语义；
- 明确后台常驻策略，消除模块 ID 特例；
- 统一事件信封、错误码、进度和日志上下文；
- 建立模块清单与静态注册一致性检查；
- 测量停用后的 Goroutine、连接、句柄和外部进程残留。

退出标准：禁用模块无法继续执行受控操作，生命周期非法迁移为 0，停用和退出资源残留为 0。

### 阶段 B：托管内核平台化

把 25 个托管模块中的重复实现收敛为共享能力：

- ArtifactManager 负责来源、缓存、下载、验证、解压、staging、安装和回滚；
- ProcessSupervisor 负责所有权、JobObject、探测、就绪、唤窗、退出和回收；
- 宿主提供标准安装策略与进程探针，适配器只能选择受控能力；
- 建立普通托管工具的契约测试套件；
- 用三类差异明显的工具验证抽象，而不是一次性重写全部模块。

退出标准：普通新工具至少 70% 逻辑来自共享包，不能再复制下载、解压和进程治理主流程。

### 阶段 C：声明式 Tool Manifest

第一种真正可外部分发的扩展不执行第三方代码，只描述：

- 身份、版本、发布者、许可证与兼容版本；
- Release 来源、资产选择和验证证据；
- 受控安装策略与布局断言；
- 受控启动参数、进程探针、就绪条件和退出策略；
- 配置 schema、敏感字段标记和宿主生成 UI；
- 网络、文件、进程等能力申请；
- 数据目录、备份、卸载和回滚规则。

Manifest 必须经过静态校验和签名。不得包含任意 PowerShell、批处理、JavaScript 或可执行安装钩子；确有特殊流程时，应先把它沉淀为宿主内建、可审计、可测试的策略。

### 阶段 D：官方扩展目录

在声明式模型稳定后建立官方目录：

- 目录只发布经过审核的扩展元数据与签名包；
- 展示发布者、来源、权限、验证等级、许可证和最近审查时间；
- 支持版本固定、灰度、撤回、回滚和不兼容阻断；
- 默认不允许未知来源静默安装；
- 本地导入必须给出清晰风险提示，不伪装成官方审核扩展。

目录价值是建立信任和更新治理，不是追求扩展数量。

### 阶段 E：受控 JSON-RPC 子进程插件

只有满足第 3.2 节条件后才进入设计与试点：

- 插件在独立低权限进程中运行；
- 宿主进行协议握手并下发短期能力 Token；
- 敏感操作只能调用 Host API，宿主复核参数、权限和用户确认；
- 所有请求支持超时、取消、幂等键和结构化错误；
- 宿主管理进程树、健康、崩溃重启上限和资源配额；
- UI 由宿主根据 schema 渲染；
- 先限定官方或白名单发布者，不立即开放无限制公共市场。

## 6. 未来产品形态

### 6.1 近期形态：可信的 Windows 工具工作台

用户看到的不是 41 个孤立页面，而是一个统一工作台：

- 知道哪些工具已安装、正在运行、可更新或异常；
- 清楚工具来自哪里、当前是什么版本、由谁启动、退出 Hanxi 后是否保留；
- 在统一运行中心管理 PID、健康、所有权与退出策略；
- 在统一更新中心查看验证等级、执行更新和回滚；
- 通过搜索、收藏、最近使用和跨模块动作完成任务。

### 6.2 中期形态：工具控制平面

Hanxi 从“工具集合”升级为本机工具控制平面：

- 工具差异被压缩为适配数据；
- 获取、验证、安装、运行和退出由平台统一治理；
- 操作具有统一状态、日志、进度、取消和诊断信息；
- 用户能够审计来源、权限、数据目录和网络行为；
- 新工具接入不再意味着复制一套基础设施。

### 6.3 长期形态：受控扩展生态

长期可形成两层扩展生态：

1. **声明式工具包**：覆盖大多数桌面工具托管场景，低风险、易审核、由宿主生成体验；
2. **受控能力插件**：覆盖少量需要代码的适配与算法场景，独立进程、显式授权、严格协议。

Hanxi 不以“任何人都能运行任意代码”为开放目标，而以“第三方可以在可验证边界内扩展 Windows 工作流”为目标。

## 7. 软件价值

插件化只有在增强产品价值时才值得实施。Hanxi 的核心价值不是插件数量，而是控制与信任。

### 7.1 对用户的价值

- **降低工具维护成本**：统一安装、更新、回滚和卸载；
- **降低运行不确定性**：区分受管、外部和脱管实例，明确退出行为；
- **提高供应链透明度**：展示来源、发布者、验证方式和风险等级；
- **减少系统杂乱**：便携数据边界、版本隔离和统一配置入口；
- **提升故障可恢复性**：安装事务、旧版本保护、诊断和明确修复动作；
- **形成工作流协同**：搜索、传输、记录、诊断和系统工具不再彼此孤立。

### 7.2 对维护者的价值

- 共性能力只修复一次，减少 25 个托管模块的重复缺陷；
- 新工具适配从“复制模块”变成“填写证据与差异”；
- 通过契约测试控制质量，降低回归成本；
- 内部模块和外部扩展共享同一治理模型；
- 主程序发布与适配数据更新可以在安全边界内逐步解耦。

### 7.3 对生态参与者的价值

- 明确、版本化、可测试的接入契约；
- 宿主提供下载、安装、进程、UI 和更新基础设施；
- 扩展开发者专注上游差异，不重复实现 Windows 生命周期治理；
- 权限和数据边界透明，减少用户对未知插件的信任成本。

## 8. 指标与决策门

指标必须记录版本、测试环境、样本量和统计口径，不使用未经复验的绝对宣传数字。

### 8.1 内部平台成熟度

| 指标 | 进入声明式扩展前目标 |
|---|---:|
| 注册模块清单与实际代码漂移 | 0 |
| 禁用模块仍可执行受控业务调用 | 0 |
| 模块停用后的 Goroutine/Ticker/连接/句柄残留 | 0 |
| 正常与异常退出后的受管孤儿进程 | 0 |
| 生命周期非法状态迁移 | 0 |
| 托管工具共享代码占比 | 普通模块 ≥ 70% |
| 安装中断后旧版本可运行率 | 100% |
| 更新失败可回滚率 | 100% |

### 8.2 扩展安全与兼容

| 指标 | 目标 |
|---|---:|
| 未签名官方目录扩展 | 0 |
| Manifest 含任意脚本或任意命令执行入口 | 0 |
| 未声明或未授权的敏感能力调用 | 0 |
| 插件崩溃导致宿主崩溃 | 0 |
| 插件升级破坏已有可用版本 | 0 |
| 协议兼容测试覆盖的受支持版本 | 100% |
| 撤回名单生效与风险通知成功率 | 100% |
| 凭据进入插件日志、事件或明文配置 | 0 |

### 8.3 产品价值

| 指标 | 判断方向 |
|---|---|
| 新托管工具接入周期 | 相比当前基线持续下降 |
| 单工具重复基础设施代码 | 持续下降，最终仅保留差异适配 |
| 安装、启动、更新成功率 | 分工具与版本统计，持续提升 |
| 用户发现运行异常所需路径 | 无需进入具体模块即可发现 |
| 更新失败后的恢复时间 | 可观测、可回滚并持续下降 |
| 扩展需求中声明式模型覆盖率 | 足够高时才证明模型有效 |
| 需要代码插件的真实需求数 | 达到至少 3 个才启动协议设计 |

插件数量、下载量和目录规模只能作为辅助数据，不能替代可靠性、安全性和实际任务完成率。

## 9. 主要风险与控制措施

### 9.1 供应链风险

**风险**：扩展源、发布账户或上游资产被篡改。  
**控制**：发布者签名、独立 digest/签名验证、验证等级、可信目录、撤回名单、版本固定和事务回滚。镜像只作为传输来源，不作为信任根。

### 9.2 权限扩大风险

**风险**：插件利用宿主权限访问进程、网络、文件、注册表或凭据。  
**控制**：默认拒绝、最小能力授权、短期能力 Token、Host API 参数复核、危险操作二次确认；不把宿主服务对象或明文 Secret 直接交给插件。

### 9.3 沙箱错觉

**风险**：把独立进程或 JobObject 宣传为安全沙箱。  
**控制**：文档明确其只提供故障与生命周期隔离；需要更强边界时评估低完整性进程、AppContainer 或专用 Broker，但不能在未实测前承诺。

### 9.4 协议兼容负担

**风险**：公开协议后内部重构受限，旧插件长期拖累。  
**控制**：版本化握手、能力协商、明确支持窗口、弃用告警、契约测试和有限的长期支持版本；内部 Go 接口不得直接等同于外部协议。

### 9.5 UI 碎片化

**风险**：第三方自带 UI 破坏一致性、可访问性和安全策略。  
**控制**：优先 schema 驱动的宿主 UI；限制扩展为标准组件和动作，不开放任意 WebView 资源。

### 9.6 质量与审核规模失控

**风险**：扩展数量超过维护者审核与响应能力。  
**控制**：官方目录采取准入制，自动静态校验与真机契约测试并行；先服务少量高价值扩展，不把数量作为目标。

### 9.7 抽象过早

**风险**：为追求统一而抹平真实工具差异，形成大量逃生钩子。  
**控制**：先迁移三类代表工具；只有重复且稳定的行为才进入共享内核。特殊流程若不能被安全策略表达，继续作为内建适配器，而不是开放任意脚本。

### 9.8 产品定位稀释

**风险**：Hanxi 退化为任意 EXE 启动器或低质量插件市场。  
**控制**：扩展必须加强“工具控制平面”或“Windows 原生工作流”，并满足来源、生命周期、数据与退出契约；无法治理的工具只提供外部链接。

## 10. 决策原则

1. 先平台化，再外部化；
2. 先声明式，再代码化；
3. 先受控目录，再讨论开放市场；
4. 插件不能绕过宿主使用敏感能力；
5. JobObject 不等于安全沙箱；
6. 内部 Go 接口不直接作为外部兼容承诺；
7. 控制平面、信任根和 Windows 高风险原语保持内建；
8. 是否拆分由边界与价值决定，不由“插件率”决定；
9. 插件化不得牺牲便携、本地优先、可恢复和可审计；
10. 当安全治理和维护能力不足时，宁可不开放。

最终判断是：Hanxi 应当演进为**可扩展但受控**的 Windows 工具控制平面，而不是任意代码插件宿主。近期最有价值的“插件化”工作，是把 41 个内建模块背后的生命周期和 25 个托管模块背后的共性能力做成稳定平台；真正的外部扩展，应从安全、声明式、宿主渲染的 Tool Manifest 开始。
