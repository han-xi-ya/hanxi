# Hanxi 界面与主题优化改造计划

> **文档状态**：提案 / 待排期
> **当前基线日期**：2026-09-18
> **适用范围**：Hanxi 桌面端 Shell、首页、主题、通用 UI 组件与现有功能页面
> **总工作量**：P50 **40 人日** / P80 **64 人日**
> **实施主线**：保留现有双栏 Shell、五色板双轴主题与生产 Token，先做代表页面和通用治理，再批量迁移
> **关联计划**：[`PLAN_OFFICIAL_MODULE_DISTRIBUTION.md`](./PLAN_OFFICIAL_MODULE_DISTRIBUTION.md)

---

## 1. 执行摘要

Hanxi 已经具备可持续演进的界面基础：双栏 Shell、`light | dark | system` 明暗轴、`teal | sky | iris | jade | onyx` 五色板、成熟的生产 Token、共享页头与 Tab、按钮和状态组件。本计划不重建主题系统，不引入第三方 UI 框架，也不把应用改造成营销式首页。

本轮改造聚焦五件事：

1. **降低 Shell 噪声并补齐响应式。** 保留“一级分类轨道 + 二级上下文面板 + 主视口”的双栏语义，优化层级、密度、选中态、折叠态和窄窗口降级。
2. **调整首页职责。** 首页从“已启用/未启用模块目录与启停入口”演进为日常工作台，呈现正在运行、待处理、可用更新、最近任务和常用入口；完整模块管理未来归独立模块中心。
3. **收敛主题方向。** Jade 浅色作为新安装默认候选方向，Teal 深色作为主要深色验收方向；现有用户继续使用已保存主题，不被迁移脚本或默认值覆盖。
4. **建立组件治理基线。** 统一 `AppIcon`、顶层 Tab、按钮、状态、页面宽度、焦点与空状态，减少页面私有实现。
5. **先代表页面、后批量迁移。** 以 Everything、WSL、FileShare、设置为样本，验证不同复杂度页面后再迁移其余页面；FileShare 优先从展示型、Hero 化风格收敛为工作台式操作界面。

本计划与官方模块分发计划分工明确：本计划负责工作台信息架构、视觉系统和前端组件治理；模块中心、安装/启用/运行/健康四维状态、真实更新数据和统一操作状态源由 `PLAN_OFFICIAL_MODULE_DISTRIBUTION.md` 提供。前端不得提前虚构第二套模块状态真相。

## 2. 当前基线

### 2.1 Shell 与导航

当前顶层布局由以下文件组成：

- `frontend/src/App.vue`：左侧 Shell 与右侧内容主视口；内容区当前统一设置 `24px 32px` Padding。
- `frontend/src/components/shell/AppSidebar.vue`：组合一级轨道和二级上下文面板。
- `frontend/src/components/shell/AppNavRail.vue`：一级分类轨道，默认宽 `64px`，可扩展到 `188px`。
- `frontend/src/constants/navigation.ts`：导航分类、设置分区、路由和展示元数据的主要来源。

现有 Shell 已支持二级面板折叠、轨道扩展、本地保存和两档响应式降级：约 `1100px` 以下隐藏二级面板，约 `760px` 以下将一级轨道降级为抽屉。基础方向正确，但仍存在层级信号偏多、内容与 Shell 重复 Padding、窄窗口状态密度较高等问题。

### 2.2 主题与生产 Token

当前主题系统已经形成稳定契约：

- `frontend/src/composables/useTheme.ts`：主题读写唯一入口。
- `frontend/src/styles/tokens.css`：生产 Token 唯一来源。
- `frontend/src/main.ts`：应用创建前初始化主题，先用本地缓存避免首帧闪烁，再以后端设置校正。
- `frontend/src/views/settings/ThemeSection.vue`：三种明暗模式和五种色板的设置入口。
- `internal/settings/store.go`、`internal/app/settings_persist.go`：后端持久化、默认值和合法性回退。
- `internal/platform/windows/darkmode.go`：Windows 原生标题栏明暗与色板映射。

现有双轴为：

- 明暗轴：`light | dark | system`
- 色板轴：`teal | sky | iris | jade | onyx`

生产默认当前仍是 `light + teal`。本计划提出 `light + jade` 作为**新安装默认方向**，必须经过主题回归、可访问性验证和发布门禁后才可修改默认值。任何默认调整只作用于没有已保存主题的新安装或明确重置主题的用户；老用户的后端设置和本地首帧缓存保持不变。

### 2.3 首页

`frontend/src/views/HomeView.vue` 当前承担：

- 应用信息和启用数量统计；
- 已启用模块卡片；
- 未启用模块卡片；
- 模块启用、停用和跳转。

这使首页同时承担日常工作台和完整模块目录两种职责。`PLAN_OFFICIAL_MODULE_DISTRIBUTION.md` 已明确要求首页继续作为工作台，完整模块管理迁往独立模块中心。因此，本轮首页重构应建立新工作台结构，但涉及安装态、健康态、更新操作的真实数据接线必须服从模块分发计划的状态投影和阶段进度。

### 2.4 通用组件与页面宽度

现有可复用基础包括：

- `frontend/src/components/ui/AppIcon.vue`
- `frontend/src/components/ui/PageHeader.vue`
- `frontend/src/components/ui/MainTabNav.vue`
- `frontend/src/components/ui/UiButton.vue`
- `frontend/src/components/ui/UiStatusChip.vue`
- `frontend/src/components/ui/UiBanner.vue`

- `frontend/src/components/ui/UiProgressBar.vue`
- `frontend/src/styles/base.css`

但组件尚未成为全仓唯一入口，页面仍存在私有图标、按钮、Tab、状态标签和重复宽度规则。当前页面宽度从约 `920px` 到 `1440px` 不等，且部分页面在 `App.vue` 内容区 Padding 内再次增加页面 Padding，形成不一致的视觉密度。

## 3. 目标

### 3.1 用户目标

1. 打开 Hanxi 后，用户先看到当前运行状态和需要处理的事项，而不是完整模块目录。
2. Shell 在宽屏、窄屏、200% 缩放和粗指针环境中都保持清晰、可操作、不过度占用空间。
3. 浅色和深色主题具有独立、稳定的层次，不依赖反色或页面局部补丁。
4. 同类按钮、Tab、状态、图标和页面宽度在不同模块中具有一致语义。
5. 复杂页面仍保持高信息密度，但不以装饰性 Hero、大面积渐变或卡片堆叠制造噪声。
6. 老用户升级后保留已保存主题、色板和 Shell 偏好，不出现视觉偏好被重置。

### 3.2 工程目标

1. 继续以 `tokens.css` 为主题和视觉语义真相源。
2. 形成可执行的页面容器、图标、Tab、按钮和状态组件使用规范。
3. 用代表页面证明迁移模式，再以清单和自动检查推进全仓迁移。
4. 将主题默认策略与主题实现解耦，允许只调整新安装默认，不迁移既有设置。
5. 首页只消费后端提供的状态投影，不在前端建立持久化业务状态副本。
6. 每一阶段可独立发布、独立回滚，避免一次性重写 Shell 和全部页面。

---

## 4. 非目标

本计划不包含：

1. 推翻双栏 Shell 或引入第三套顶层导航模型；
2. 重写五色板双轴主题系统；
3. 引入第三方 UI 框架、Pinia 或 vue-router；
4. 建设第三方插件市场或动态微前端平台；
5. 在本计划内实现完整模块中心、模块安装/卸载或四维状态后端；
6. 用前端模拟值冒充真实运行、更新、健康或任务状态；
7. 一次性重写所有功能页面；
8. 追求营销官网式 Hero、玻璃拟态、大面积渐变、装饰性持续动画或过度圆角；
9. 强制把所有页面做成相同布局，牺牲终端、表格、日志和复杂工作区的任务特性；
10. 修改老用户已保存的主题、色板或 Shell 偏好；
11. 把静态设计稿 HTML 直接嵌入 Vue 业务页面；
12. 在缺乏真实模块状态 API 时提前承诺“已安装、健康、可更新”等产品语义。

## 5. 设计原则

### 5.1 工作台优先

首页和功能页首先服务“查看状态、采取动作、确认结果”，而不是展示品牌或功能数量。首屏优先显示当前运行、待处理和最近活动。

### 5.2 保留成熟系统，修正不一致

主题 Token、双栏 Shell、异步页面加载和现有 UI 组件是基线，不以重构名义另建并行系统。问题通过语义 Token、共享组件和页面容器治理解决。

### 5.3 紧凑但不拥挤

默认桌面布局保持高信息密度；通过分组、留白、字体层级和边界降低噪声，而不是无限增加卡片、阴影和背景层。

### 5.4 状态不只依赖颜色

运行、等待、警告、失败、停用等状态至少同时使用文字、图标、形状或结构之一。颜色用于加强识别，不是唯一载体。

### 5.5 渐进披露

首页只呈现摘要和高频动作；完整模块属性、安装管理、版本治理和诊断进入模块中心或对应详情页。危险操作不与日常动作并列争抢视觉注意力。

### 5.6 真实数据优先

没有可靠 API 的信息不进入生产首页。允许用降级卡片、空状态或隐藏分区表达“能力尚未接线”，禁止长期保留样例数据。

### 5.7 先代表、后批量

先用 Everything、WSL、FileShare、设置覆盖标准列表、多 Tab、展示型工作区和表单四类页面，再固化规范和迁移模板。

### 5.8 可回滚优先

Shell、主题默认和首页信息架构应拆分开关或独立提交。任一部分出现回归时，可回退到旧首页或旧默认，不影响主题读取和功能调用。

## 6. 主题策略

### 6.1 保留五色板双轴模型

继续使用：

```text
明暗：light | dark | system
色板：teal | sky | iris | jade | onyx
```

任何主题精修优先改动 `frontend/src/styles/tokens.css` 的语义变量，不在页面内新增裸颜色。页面只能在确有业务含义时使用状态色；品牌色、选中态、表面层次、边框和文字必须来自 Token。

### 6.2 新安装默认方向

建议方向：

- **Jade 浅色**：新安装的默认候选，承担安静、清晰、长期使用的主方向。
- **Teal 深色**：主要深色方向和深色回归基准，验证独立表面层次、边框和状态对比。
- **Sky / Iris / Onyx**：继续作为完整支持的可选色板，不降级为实验功能。

最终修改 `DefaultSettings()` 前必须满足：

1. 五色板在 light/dark/system 下完成视觉回归；
2. Jade 浅色达到正文、控件、焦点、状态和禁用态对比要求；
3. Teal 深色在标题栏、Shell、主视口和弹层间层次稳定；
4. Onyx 的高对比职责没有被通用 Token 改动削弱；
5. 安装升级测试证明有保存值的用户不被覆盖；
6. 产品发布说明明确“新安装默认变化”，不描述为强制迁移。

### 6.3 老用户保持已保存主题

主题真相源继续以后端设置为准，本地 `hanxi.theme` 和 `hanxi.accent` 仅用于首帧防闪。升级逻辑遵循：

| 用户状态 | 行为 |
| --- | --- |
| 后端已有合法 Theme/Accent | 原样保留 |
| 后端缺失，但本地缓存合法 | 首帧使用缓存，并按既有初始化流程校正 |
| 全新安装、没有保存值 | 使用发布时确定的新默认候选 |
| 用户点击“重置主题” | 明示将恢复当前版本默认，不静默执行 |
| 保存值非法或损坏 | 使用合法回退，并记录可诊断信息 |

不得通过一次性迁移脚本把所有 `teal` 改为 `jade`，也不得仅凭“值等于旧默认”判断用户没有主动选择 Teal。

### 6.4 Token 治理

重点检查并收敛：

- `--surface-chrome`、`--surface-page`、`--surface-panel`、`--surface-soft`；
- Hover、Selected、Focus、Disabled 的层级关系；
- 正文、次要文字、弱文字在浅色和深色下的对比；
- 状态色在五色板中的语义稳定性；
- 边框在高密度表格、卡片、输入框和 Shell 中的可见度；
- 字号、控件高度、圆角、阴影和动效的使用边界；
- Windows 原生标题栏与 `internal/platform/windows/darkmode.go` 的同步映射。

### 6.5 主题验收基准

视觉基准至少覆盖：

- Jade 浅色桌面：`workbench-home-jade-light.png`
- Teal 深色桌面：`workbench-home-teal-dark.png`
- Jade 浅色窄窗口：`workbench-home-jade-narrow.png`
- 五色板 × light/dark；
- `system` 跟随系统切换；
- 应用冷启动首帧；
- Windows 标题栏、Shell、弹层、表格、输入、终端和危险状态。

## 7. 信息架构

### 7.1 Shell 层级

保留三层结构：

```text
一级分类轨道
  └─ 二级上下文面板
       └─ 当前页面主视口
```

优化方向：

- 一级轨道只表达全局类别、首页、通知和设置，不承载页面级动作；
- 二级面板只表达当前类别、设置分区或工作台上下文；
- 主视口内不再重复创建第三个永久侧栏，确有需要时使用局部 Tab、工具条或可折叠检查器；
- 减少重复边框、徽标和状态点，同一信息不在轨道、面板和页面同时强调；
- 展开、折叠、Flyout 和抽屉保持同一导航语义和焦点顺序。

### 7.2 新首页结构

首页目标结构以现有设计资产为基准：

1. **紧凑页头**：标题、简短状态说明、必要的全局动作；
2. **摘要区**：正在运行、待处理、可用更新；
3. **正在运行**：展示活跃模块、托管进程或进行中的服务；
4. **待处理 / 更新**：合并需要用户决策的事项，不把普通通知全部抬升到首页；
5. **最近任务**：安装、下载、转换、同步、投递等统一操作记录；
6. **常用入口**：最多 4–6 个，来源可先沿用固定/最近使用，后续接入用户固定能力；
7. **空状态**：没有运行项或待处理项时保持简洁，不用大面积插画填充。

首页不再展示完整“已启用/未启用”模块卡片目录。迁移期若模块中心尚未完成，可保留明确标记的“管理模块”入口或兼容弹层，但不把旧目录继续作为首页主体。

### 7.3 与模块中心的边界

| 能力 | 首页 | 模块中心 |
| --- | --- | --- |
| 正在运行摘要 | 是 | 可查看详情 |
| 待处理与更新摘要 | 是 | 完整列表与操作 |
| 最近任务 | 摘要 | 完整历史和诊断 |
| 常用入口 | 是 | 否 |
| 全部模块目录 | 否 | 是 |
| 安装/卸载 | 仅跳转或上下文动作 | 是 |
| 启用/停用 | 仅高频安全动作或跳转 | 是 |
| 来源、权限、磁盘占用 | 否 | 是 |
| 四维状态详情 | 摘要 | 是 |

### 7.4 数据接线策略

- T2 可先使用当前已有的运行、导航、应用信息和任务数据形成真实最小首页。
- “可用更新”“健康”“安装态”若无真实后端投影，分区应隐藏或显示不可操作的明确说明，不填充模拟数据。
- 当模块分发计划 Phase 1–2 提供 Catalog 和四维状态后，首页改为消费统一投影。
- 首页只缓存展示偏好，不持久化模块业务状态。

## 8. 组件治理

### 8.1 `AppIcon`

- 功能图标统一通过 `AppIcon.vue` 和 `constants/icons.ts` 注册表输出；
- 默认装饰性图标使用 `aria-hidden`，独立按钮图标必须提供可访问名称；
- 禁止页面复制相同 SVG 路径或用 Emoji 充当生产功能图标；
- 图标尺寸限定为少量语义档位，颜色默认继承 `currentColor`；
- 模块图标、动作图标和状态图标职责分离，不用品牌图标代替状态含义。

### 8.2 顶层 Tab

- 顶层功能分区统一使用 `MainTabNav.vue`；
- 必须保留 `tablist`、`tab`、`aria-selected` 和 Tab/Panel 关联；
- 明确溢出策略：优先横向滚动或紧凑标签，不在窄屏任意换成两行按钮墙；
- 主题设置的分段选择与业务 Tab 共用视觉 Token，但保留不同语义；
- 禁止每个页面重新定义一套下划线、胶囊或卡片 Tab。

### 8.3 按钮

- 常规动作统一使用 `UiButton.vue` 或受控的全局 `.btn` 契约；
- 语义限制为 Primary、Secondary、Danger、Ghost，不按页面新增近义变体；
- 一个操作区原则上只有一个 Primary；
- 危险操作不通过红色填满整个页面，需配合确认、说明和权限边界；
- 图标按钮必须具备 Tooltip 或可访问名称，并满足最小命中尺寸。

### 8.4 状态

- 状态标签统一使用 `UiStatusChip.vue` 或其后续受控扩展；
- 基础语义为 `positive | information | warning | danger | neutral`；
- 业务状态文本保持具体，如“运行中”“等待重启”“下载失败”，不只显示“正常/异常”；
- 状态 Chip 不替代 Banner、空状态或任务进度；
- 同一业务状态在首页、模块中心和详情页使用一致词汇。

### 8.5 页面宽度与容器

建立三档语义容器，替代散落的固定宽度：

| 容器 | 建议用途 | 建议上限方向 |
| --- | --- | ---: |
| Standard | 设置、表单、普通详情 | 960–1040px |
| Workbench | 首页、复杂模块、双列工作区 | 1160–1240px |
| Wide/Data | 大表格、文件列表、日志工作区 | 1360–1440px |

最终数值在 T0 通过代表页面验证后固化为 Token 或 `PageContainer` 组件。页面容器负责宽度和居中；Shell 负责视口安全边距。禁止 Shell 和页面双重堆叠同等级 Padding。

### 8.6 迁移规则

- 新页面必须直接使用治理后的组件和容器；
- 旧页面按代表页模板逐批迁移，不要求一次清零；
- 每批迁移附组件使用清单和视觉回归；
- 对终端、日志、代码预览等特殊区域允许受控例外，但需说明原因；
- 不为了“统一”把复杂页面拆成大量无意义卡片。

## 9. 响应式与无障碍

### 9.1 响应式目标

至少覆盖以下窗口与缩放组合：

- 宽桌面：`≥ 1200px`；
- 中等窗口：`761–1199px`；
- 窄窗口：`390–760px`；
- 最小支持宽度：`320px`，允许部分高密度区域水平滚动；
- 100%、125%、150%、200% 系统或浏览器缩放。

### 9.2 Shell 降级

- 宽桌面：一级轨道 + 二级面板常驻；
- 中等窗口：一级轨道常驻，二级面板按上下文 Flyout；
- 窄窗口：导航降级为可关闭抽屉，主视口获得完整宽度；
- 抽屉打开后焦点进入抽屉，关闭后返回触发按钮；
- 遮罩、Esc、外部点击和窗口变化具有一致关闭行为；
- Safe Area 用于顶部、左右和底部边距。

### 9.3 内容重排

- 首页桌面双列，窄窗口单列；
- 摘要项可从横排变为网格或纵向，不压缩到不可读；
- 表格在窄窗口优先保留关键列，次要信息进入详情或折叠区；
- Tab 和工具条允许横向滚动，但关键主动作保持可见；
- 长路径、版本号和命令使用可复制、截断和完整提示组合。

### 9.4 无障碍要求

- 所有交互可通过键盘完成；
- `:focus-visible` 清晰，不能被容器裁切；
- 粗指针环境最小命中尺寸不低于现有 `44px` 基线；
- 正文和重要控件目标达到 WCAG 2.2 AA 对比要求；
- 状态不只依赖颜色；
- 图标按钮、抽屉、Tab、对话框、进度和动态通知具备正确语义；
- 尊重 `prefers-reduced-motion`，不使用装饰性持续动画；
- 200% 缩放下不丢失主要功能、不发生双向页面级滚动；
- 动态任务更新使用克制的 Live Region，不对高频日志逐行播报。

考虑 T0 契约、T1 基础和 T3 组件的前置依赖，不能按总人日简单除人数：

- **2 人 P50：约 5–6 周；P80：约 8–9 周**；
- **3 人 P50：约 4–5 周；P80：约 6–7 周**。

可并行关系：

- T1 后半段可与 T2 数据接线准备并行；
- T2 后半段可与 T3 组件测试并行；
- T4 可按 Everything/WSL 与 FileShare/设置拆成两组；
- T5 批量迁移可按页面类型并行，但最终主题回归和发布门禁必须统一收口。

## 14. 发布与回滚

### 14.1 发布策略

1. **内部基线版**：只发布 T1 Shell/Token 精修，验证全仓视觉影响；
2. **工作台预览版**：新首页通过功能开关或开发通道启用；
3. **代表页面版**：Everything、WSL、FileShare、设置完成迁移后扩大使用；
4. **批量迁移版**：迁移高频页面并冻结新增私有样式；
5. **默认策略版**：仅在全部门禁通过后，决定是否让 Jade 浅色成为新安装默认。

每一版都应附：

- 视觉与行为变更说明；
- 已知例外页面；
- 老用户偏好保持说明；
- 模块中心和首页能力边界；
- 回滚条件和版本。

### 14.2 功能开关与兼容

- 新首页在稳定前保留旧首页组件或可恢复路径；
- 新旧首页消费同一真实数据接口，不各自持久化状态；
- 主题默认值变更不需要迁移老用户设置；
- Shell 本地偏好键保持兼容，除非有独立迁移和回滚测试；
- 模块中心未完成时，首页提供受控过渡入口，不复制一套临时模块中心。

### 14.3 回滚触发条件

出现以下任一情况应回滚对应阶段，而不是继续叠补丁：

- 老用户主题或 Shell 偏好被重置；
- 核心导航在 390px、200% 缩放或键盘模式下不可用；
- 主题对比出现严重回归；
- Everything、WSL、FileShare 的关键操作路径失败；
- 首页显示不真实或互相矛盾的运行/更新状态；
- Token 改动导致大面积低频页面不可读；
- 原生标题栏与应用主题明显冲突。

### 14.4 回滚方式

- T1：回退 Token/Shell 提交，保留主题存储结构；
- T2：关闭新首页开关或恢复旧首页入口，不回滚业务设置；
- T3/T4：按组件或代表页面独立回退，避免全仓倒退；
- T5 默认策略：恢复新安装默认值，绝不批量改写用户保存值；
- 模块状态接线：回退到只读摘要或隐藏未稳定分区，不在前端伪造状态。

## 16. 与官方模块分发计划的衔接

本计划必须遵守 [`PLAN_OFFICIAL_MODULE_DISTRIBUTION.md`](./PLAN_OFFICIAL_MODULE_DISTRIBUTION.md) 的以下边界：

1. **首页是工作台，模块中心是完整模块管理入口。** 本计划先调整首页职责，不在首页复制未来模块中心。
2. **不再用单一 `Enabled` 推断全部状态。** 首页未来消费 Delivery、Policy、Runtime、Health/Currency 四维状态投影。
3. **前端不持久化第二份状态真相。** 安装、启用、运行、健康、版本和操作进度都以后端 Catalog、Registry、Supervisor 和 Operation 为准。
4. **Phase 1–2 是状态接线关键依赖。** 在此之前，首页只展示当前真实可获取的运行与任务数据。
5. **模块中心入口属于内建控制平面。** Shell、首页、设置、导航和通知继续随宿主交付。
6. **复杂模块拆包不是本计划目标。** OCR、FileShare sidecar 和 WSL 后置策略由模块分发计划管理；本计划只治理其宿主 UI。
7. **未安装或停用模块的入口策略统一。** 导航、搜索、托盘、常用入口和首页必须消费相同可见性投影。
8. **最近任务应逐步接入统一 Operation。** 下载、安装、更新、转换、同步等操作共享进度、取消、错误和恢复语义。

建议协同里程碑：

| UI 计划 | 模块分发计划 | 衔接产物 |
| --- | --- | --- |
| T0–T1 | Phase 0 | 状态词汇、组件契约、导航与页面边界 |
| T2 | Phase 1 | 首页摘要投影、模块中心入口、逻辑安装态展示边界 |
| T3–T4 | Phase 1–2 | 四维状态组件、统一调用门错误和 Operation 展示 |
| T5 | Phase 2+ | 批量入口可见性、最近任务、更新和健康摘要 |
