## 1. 总体结论

**Hanxi 已经具备 Windows 本地工具运维工作台的基础。当前最需要的不是继续增加工具，而是收稳安全边界、后台任务和状态一致性。**

主要矛盾是：工具集成速度快于公共能力的收敛速度。同一种下载、启停、版本加载逻辑复制到多个模块后，修复和约束没有同步，导致功能外观统一，实际可靠性却不一致。

建议未来 1～2 个迭代暂停非必要的新工具接入，优先修复高风险路径，随后发展统一任务中心、更新中心和诊断能力。

优先顺序：

**数据与文件安全 → 进程和下载生命周期 → 异步状态一致性 → 公共能力收敛 → 任务、更新与诊断中心 → 新工具扩展。**

## 3. 应保留的架构资产

### 3.1 技术路线适合产品

Go + Wails + Vue 配合 Windows 原生 API，适合本地工具管理：

- Go 负责进程、文件、网络与系统操作。
- Vue 负责状态展示与操作入口。
- JobObject、DPAPI、按需提权是合适的基础能力。

不建议为了架构形式引入微服务、跨平台适配层，或者强行接入 Pinia / vue-router。

### 3.2 模块化与公共基础已经成立

- 后端装配根集中注入平台、配置、模块、事件和 Wails 服务。
- 进程与版本引擎通常脱离 Wails，具备通过接口做故障注入的条件。
- 前端已有设计 token、公共组件、错误边界、事件和轮询 composable。
- 视图已采用异步组件按需加载，不能继续把“全部视图静态导入”作为当前问题。
- `usePolling` 已考虑 KeepAlive 停启，`useWailsEvent` 有作用域清理；缓存页面继续监听业务事件不应一概判断为泄漏。
- Snipaste 等部分模块已有正确的下载去重机制，可以作为迁移范例。
- WSL 已实现白名单操作、下载重定向主机限制、提权退出码传播和可注入探针。

### 3.3 工程门禁已有基础

类型检查、前端测试、Go vet、CI race 测试与绑定一致性检查均已存在。

当前重点不是简单增加测试数量，而是覆盖：并发、失败、取消、恢复、关闭以及跨层状态同步。

## 4. 后端问题与修复方向

本章问题以静态调用链审阅为依据，未声称真机复现。优先级用于安排修复顺序，不是 CVSS 安全评分。

### B01. frpc 版本删除缺少目录边界校验

**优先级：高。分类：静态确认缺陷。**

证据：

- `internal/modules/frpc/service.go:208–210`：版本参数仅做空白裁剪。
- `internal/modules/frpc/version/manager.go:243–250`：版本字符串直接拼入路径并检查存在性。
- `internal/modules/frpc/version/manager.go:224–230`：对解析出的目标执行递归删除。

触发条件：异常或恶意 Wails 绑定参数包含路径分隔符及父目录跳转，规范化后的路径越过版本目录，且目标目录存在。

影响：可能删除版本目录之外、Hanxi 进程有权限删除的目录。管理员身份会扩大影响面。

边界：这是绑定 API 输入边界问题，不是已证实的未认证远程删除漏洞；正常界面通常不会生成此类参数。

修复建议：

1. 严格校验版本语法。
2. 危险操作只接受已枚举安装清单中的版本标识。
3. 文件操作前再次验证规范化路径归属。
4. 排查其他卸载、导入与解压入口，统一安全契约。

### B02. 快传共享目录可被已有 junction / symlink 穿透

**优先级：高。分类：静态确认缺陷，利用有前提。**

证据：

- `internal/modules/fileshare/server.go:288–308`：只做词法层面的 `Clean/Join/Rel` 检查。
- `internal/modules/fileshare/server.go:357–404`：下载通过普通文件 API 访问目标，会跟随链接。
- `internal/modules/fileshare/server.go:430–443`：上传沿用同一目录检查方式。
- `internal/modules/fileshare/server.go:119–145`：监听全部 IPv4 接口，未见认证层。
- `internal/modules/fileshare/service.go:29–43`：共享目录默认值包含用户目录回退逻辑。

触发条件：用户开启共享，共享树中已有指向树外目录的 Windows junction 或 symlink，对端可访问服务端口。

影响：可能读取共享根目录之外的文件；开启上传时可能向链接目标目录新增文件。仍受 Hanxi 进程文件权限约束。

边界：没有证据说明远程上传可直接创建链接，也不能表述为默认公网暴露；网络、防火墙和用户操作均影响实际可达性。

修复建议：

- 使用能够限制实际文件访问根目录的机制，并测试 Windows reparse point 行为。
- 不要只做一次 `EvalSymlinks` 后再普通打开，避免检查与使用之间的换链竞态。
- 增加会话访问码或配对、指定网卡绑定和共享范围提示。
- 默认共享专用目录，不应在 Downloads 不存在时回退到整个用户目录。

### B03. frpc 重复启动破坏进程代际归属

**优先级：高。分类：静态确认竞态。**

证据：

- `internal/modules/frpc/service.go:286–328`：启动入口无运行态防重复。
- `internal/modules/frpc/instance/manager.go:38–50`：复用同一个 Instance。
- `internal/modules/frpc/instance/instance.go:142–208`：启动锁仅串行化调用，新启动覆盖共享 `cmd/job`。
- `internal/modules/frpc/instance/instance.go:313–330`：旧 `wait()` 访问并清理共享字段。

触发条件：同项目重复启动，或停止尚未回收完成便再次启动。

影响：旧进程退出可能关闭新 Job、清空新进程引用；特定调度下可能出现错误 Wait 或空指针路径。先启动等待协程、后登记 Running 的顺序也可能使快速退出状态被覆盖。

修复建议：

- 运行态 Start 幂等或明确拒绝。
- Restart 必须经过 Stop → 等待 done → Start。
- 每次运行创建独立对象，持有自己的 `cmd/job/done/generation`。
- 旧运行只能清理自己的资源，只有当前代能更新公共状态。

### B04. 下载互斥没有覆盖实际后台安装

**优先级：高。分类：静态确认缺陷。**

证据：

- `internal/modules/frpc/service.go:151–184`。
- `internal/modules/ccswitch/service.go:166–204`。
- `internal/modules/ccswitch/version/manager.go:179–184,295–302`。
- `internal/modules/frpc/version/manager.go:397–425`。

问题：锁在 goroutine 启动后随 RPC 返回而释放，后台任务仍在进行；下层没有补充覆盖整个安装的互斥。

触发条件：同一未安装版本在第一次下载完成前再次请求安装。

影响：重复下载、重复进度、同目录交错写入；失败任务清理目录时可能破坏另一任务结果。下载、导入、卸载之间也需要统一协调。

修复建议：

1. 按模块和版本登记在途任务。
2. 下载、导入、卸载共享互斥规则。
3. 每个任务使用独立暂存目录。
4. 校验完成后提交到最终目录，失败只清理自己的暂存资源。

可参考：`internal/modules/snipaste/service.go:69–82`。

### B05. frpc 配置加载错误被吞，后续保存可能覆盖原项目库

**优先级：高。分类：静态确认数据丢失路径。**

证据：

- `internal/modules/frpc/store.go:26–32`：初始化忽略加载错误。
- `internal/modules/frpc/store.go:39–50`：读取或 JSON 解析失败后内存保持空集合。
- `internal/modules/frpc/store.go:131–146`：后续按内存集合保存。

触发条件：项目文件损坏，或启动时暂时不可读但随后可写；用户看到空列表后新建项目。

影响：原文件被新集合覆盖，降低恢复机会。

补充：`internal/settings/store.go:178–183` 等更新路径先改内存再持久化，失败时可能出现内存与磁盘不一致。

修复建议：

- 区分首次不存在与读取、解析失败。
- 加载异常时明确提示，并禁止正常覆盖原文件。
- 对项目类数据保留 last-known-good 备份。
- 复制修改 → 写盘成功 → 替换内存，失败不提交新状态。

### B06. 凭据保护不一致，且运行配置可能残留

**优先级：中高。分类：明文路径与失败处理静态确认。**

证据：

- `internal/settings/store.go:12–34,361–367`：微信 BotToken、ContextToken 随普通 JSON 配置保存。
- `internal/modules/frpc/store.go:77–84`：DPAPI 加密失败时继续保留并保存原始 token。
- `internal/modules/frpc/store.go:58–63`：解密失败未明确转成凭据不可用。
- `internal/modules/frpc/service.go:309,333–339,361–364`：运行 TOML 含明文凭据，显式停止与应用关闭的清理路径不一致。

影响：备份、分享和迁移目录时可能泄露凭据；DPAPI 失败被隐藏；应用退出后可能留下含凭据的运行配置。

边界：Windows 文件可读范围取决于实际 ACL，不能把 `0644` 直接等同于所有本机用户可读。未读取真实凭据，也没有声称 DPAPI 失败已在用户机器发生。

修复建议：

- 统一 SecretStore，普通配置只保存秘密引用或密文。
- 加密失败必须显式失败，不静默降级。
- 解密失败提示重新输入凭据。
- 运行配置目录设置适当用户 ACL，覆盖进程退出、模块关闭和下次启动残留清理。
- 明确便携数据与机器绑定秘密的迁移边界。

### B07. 快传停止持锁等待请求，超时后未完整回收

**优先级：中高。分类：静态确认生命周期缺陷。**

证据：

- `internal/modules/fileshare/service.go:144–153`：持服务写锁调用停止。
- `internal/modules/fileshare/service.go:118–126`：传输回调需要同一服务读锁。
- `internal/modules/fileshare/server.go:169–190`：持引擎锁调用三秒 Shutdown，超时后未 Close 即丢弃引用。
- `internal/modules/fileshare/server.go:596–602,729–730`：部分 handler 需要获取引擎锁。
- `internal/modules/fileshare/server.go:183–185,647–655`：采样循环读取可变停止通道。

触发条件：停止时存在活动传输或请求，其结束处理正在等待上述锁。

影响：Shutdown 与 handler 相互等待直到超时；界面已显示停止，但活动连接可能继续。采样循环也存在错过停止信号的路径。

修复建议：锁内摘取稳定资源，锁外 Shutdown；超时 Close 兜底并等待退出。采样协程捕获本代停止通道，不循环读取可变共享字段。

### B08. 缺少可信校验值时，frpc 下载校验降级放行

**优先级：中高。分类：静态确认信任策略缺口。**

证据：

- `internal/modules/frpc/version/manager.go:140–154`：缺少 expected 时只计算文件自哈希，跳过可信值比较。
- `internal/modules/frpc/version/manager.go:279–318`：文件与校验信息存在第三方代理回退。
- `internal/modules/frpc/version/downloader.go:27–31`：远程元信息也存在代理回退。

影响：文件自哈希只能提供摘要，不能证明来源真实性；文件与校验值都来自同一不可信来源时，也不能独立建立信任。

边界：没有证据表明镜像已被入侵。这是校验策略问题，不是已发生的供应链事故。

修复建议：明确区分传输完整性、官方来源认证与未验证安装。可信校验不可得时，按明确策略阻断或要求用户确认，不能呈现为正常可信校验成功。

### B09. WSL 旧体检轮次可能覆盖新结果

**优先级：中。分类：静态确认异步状态缺陷。**

证据：`internal/modules/wsl/service.go:120–127,148–175`。

问题：新体检取消旧 context，但旧任务返回后仍可能无条件推送事件，事件没有轮次标识。

触发条件：快速启动两次体检，旧轮次取消后的失败事件晚于新轮次成功事件到达。

修复建议：为体检分配 generation/request ID；事件发布和缓存写入前验证轮次及取消状态，前端同样过滤旧轮次。

## 5. 前端问题与修复方向

### F01. 远程失败阻断本地已安装资产展示

**优先级：高。分类：静态确认功能缺陷。**

证据：`frontend/src/views/MarkerOnView.vue:126–141,450–461`，多个托管视图存在同构模式。

问题：将远程 Releases、本地版本与当前版本放进同一个 `Promise.all`，全部成功才写回。

触发条件：已有本地安装，进入页面时远程请求失败或持续挂起。

影响：本地成功结果被丢弃，可能误显示尚未安装，影响切换、定位和卸载等本地操作。

修复建议：本地资产与远程清单独立加载、独立报错；明确区分加载中、失败、缓存和真实空列表。

### F02. Everything 搜索丢失最后输入

**优先级：中高。分类：静态确认竞态。**

证据：`frontend/src/composables/useEverythingSearch.ts:54–99`。

触发条件：A 查询在途，用户输入 B，防抖到期时 A 尚未完成；或在途时清空输入。

问题：搜索中直接返回，B 不补发；清空等操作没有及时使旧请求失效。

影响：输入 B 却显示 A，清空后旧结果还可能重新出现。

修复建议：参数变化立即失效化旧结果；采用 latest-wins 或当前请求结束后执行最新待查询值。

### F03. 微信扫码关闭后可重新启动轮询

**优先级：中高。分类：静态确认生命周期缺陷。**

证据：`frontend/src/composables/useWechatBot.ts:209–302,702–704`。

触发条件：取码或扫码检查请求在途时关闭窗口；旧响应返回后继续启动轮询或重新取码。

问题：关闭仅清理当前 timer，没有使在途会话失效。

影响：关窗后继续请求；反复开关可能产生多条轮询而只能追踪一个 timer。

修复建议：扫码 session ID 与关闭、卸载失效化；每个 await 后验证当前会话；启动前回收旧 timer。

### F04. 图片、文件发送失败仍显示发送中

**优先级：中。分类：静态确认状态缺陷。**

证据：

- `frontend/src/composables/useWechatBot.ts:482–561`。
- `frontend/src/components/wechatbot/WechatBotChatFlow.vue:213–214`。

问题：失败分支追加错误消息，却不将原发送气泡从 pending 改为 failed。

修复建议：统一文本、图片、文件的 pending → sent/failed 状态机，保留消息 ID 供异常分支回填。

### F05. Memo 删除没有确认或撤销

**优先级：中。分类：交互数据丢失风险，不是安全漏洞。**

证据：

- `frontend/src/views/MemoView.vue:178–185,305`。
- `internal/modules/memo/service.go:252–269`：后端直接删除并保存，非软删除。

触发条件：误点便签删除按钮。

修复建议：最低成本复用 `useConfirm`；如追求高频效率，则采用可恢复软删除和撤销。

### F06. 模态与部分操作缺少键盘可访问性

**优先级：中。分类：静态确认交互缺口。**

证据：

- `frontend/src/components/wechatbot/WechatBotBindModal.vue:38–55`。
- `frontend/src/components/everything/EverythingResultsPanel.vue:46–60`。

问题：微信绑定模态缺少 dialog 语义、标题关联、初始焦点、焦点圈定、Esc 和返回焦点；部分复制操作仅绑定非聚焦单元格 click。

修复建议：复用现有确认、输入对话框的可访问行为，提供语义化按钮和键盘替代，不必引入新 UI 框架。

### F07. 轮询与事件之间可能发生旧状态覆盖

**优先级：中。分类：待验证风险。**

证据：

- `frontend/src/composables/usePolling.ts:36–60`：没有统一限制 async tick 并发或失效化在途响应。
- `frontend/src/views/MarkerOnView.vue:145–147,329–332`：轮询响应和事件均可直接赋值。

风险：慢轮询超过间隔时重叠；旧快照 RPC 可能晚于新事件返回，使状态回退。

下一步：用可控 deferred promise 构造确定性时序，验证后引入请求代际或版本化快照规则。不能仅凭存在轮询就断言实际泄漏。

## 6. 工程与发布流程

### E01. ESLint 目前主要是观察基线

`frontend/eslint.config.js:1–3,29–40` 将规则统一降为 warning。因此 lint 通过不等于相关质量规则严格阻断。

建议：新代码和已治理模块先收紧；存量保留基线但禁止新增警告，避免一次性全仓改动。

### E02. Release 与普通 CI 门禁不一致

- `.github/workflows/ci.yml:63–75` 包含前端测试与 Go 检查。
- `.github/workflows/release.yml:65–76` 未执行前端单元测试，也未显式要求 tag 对应提交已通过普通 CI。

建议：收敛共用验证入口，让实际发布必须经过一致门禁。

### E03. 发布版本元数据缺少一致性校验

- `.github/workflows/release.yml:84–97` 使用 tag 命名产物。
- `build/windows/info.json:3–7` 和 `build/config.yml:11` 固定为 `0.3.0`。

条件性风险：后续发布新 tag 未同步元数据时，文件名与文件属性版本不一致。当前不能仅因固定版本就断言现有发布已经错误。

建议：统一版本来源，发版前校验 tag、应用版本和 Windows 资源版本。

### E04. 文档存在事实与规划漂移

- `docs/DEVELOPMENT.md:109–114` 称 `task build` 自动 tidy 和生成绑定，但当前构建依赖链没有对应步骤。
- `build/windows/Taskfile.yml:33–53`、`build/Taskfile.yml:72–94` 是实际构建入口依据。
- 产品战略文档仍有旧模块数量与静态加载描述，开发计划的持续扩量与战略收束目标存在冲突。

建议：文档明确区分当前实现、已批准方向和历史决策；建立单一优先级来源。

### E05. npm 安装冷却配置当前未生效

运行前端检查时，npm 报告不识别 `minimum-release-age`。`frontend/.npmrc:1–5` 已明确说明 npm 会忽略该配置。

这不是隐藏实现错误，但意味着不能把当前 npm 安装流程视为已获得该冷却保护。建议明确工具链实际提供的供应链约束，不把注释或兼容配置当作已启用门禁。

## 7. 架构优化方案

### 7.1 收敛四类共同行为

| 公共能力 | 统一解决的问题 |
| --- | --- |
| 操作任务模型 | ID、取消、进度、错误、完成、重复操作和关闭回收 |
| 进程运行模型 | 独立运行资源、启动幂等、停止等待、旧实例隔离 |
| 安装事务模型 | 下载、可信校验、暂存、提交、失败恢复、卸载互斥 |
| 配置与凭据模型 | 写盘一致性、加载失败保护、备份恢复、加密失败处理 |

### 7.2 渐进迁移，不做万能基类

先迁移两个代表场景：

1. frpc：覆盖多实例、日志、启动、停止和重启。
2. 一个典型 GUI 托管工具：覆盖版本下载、安装切换和外部进程。

公共契约验证成立后再逐模块迁移。保留各工具特有的单实例协议、退出语义和便携目录布局，避免巨型 BaseService 通过大量条件分支容纳所有差异。

### 7.3 前端统一异步契约

- 参数变化、关闭、卸载必须使旧请求失效。
- 取消 timer/context 不等于在途请求不会返回。
- 每个异步结果写回前验证任务 ID 或 generation。
- 本地状态不依赖外网成功。
- 请求失败与空列表不能共用语义。
- 不仅拆组件和 CSS，还要收敛资产加载与运行状态同步模型。

### 7.4 性能优化必须有测量依据

建议建立以下基线：

- 冷启动与首次可交互耗时。
- 页面首次加载和后续切换延迟。
- 连续访问多个页面后的缓存内存与事件订阅数。
- 连续启停模块后的 goroutine、句柄和连接数。
- 版本目录扫描、重复哈希、日志读取与渲染成本。
- 下载和大文件传输的峰值内存与吞吐。

先确认热点，再考虑缓存、增量扫描、日志尾读和虚拟列表。不要为了工作集数字频繁强制 GC，也不要在没有基准时承诺绝对内存目标。

## 8. 测试补强清单

### 8.1 安全与数据边界

- 异常版本 ID 必须在任何文件操作前拒绝。
- junction、symlink 和换链场景不能逃出共享根。
- 缺失、错误或不可信校验信息的安装策略。
- JSON 损坏、不可读、磁盘写失败、DPAPI 失败不允许静默覆盖或降级。

### 8.2 生命周期与并发

- 重复 Start、Stop 后立即 Start、瞬时退出、旧 Wait 晚到。
- 同版本并发下载、下载与卸载竞争、失败清理不影响成功任务。
- 活动传输期间 Stop、Shutdown 超时强制关闭。
- 连续启停后 goroutine、ticker、连接和句柄不持续增长。
- WSL 旧轮次取消后故意延迟返回，不得修改新轮次状态。

### 8.3 前端异步与交互

- 断网时已有安装仍可展示和操作。
- 慢搜索时最新输入最终生效，清空后旧结果不回填。
- 关闭扫码框、切页或卸载后，在途响应不再重建任务。
- 所有发送类型失败后气泡明确进入 failed。
- Memo 删除具备确认或可恢复机制。
- 关键模态键盘全流程、焦点返回和读屏语义。

优先采用注入式 runner、downloader、文件系统及同步屏障构造确定性测试，避免依赖 Sleep 和人工快速点击。真实系统能力另设明确授权的 Windows 集成测试层。

## 9. 产品定位与后续路线

### 9.1 建议定位

**面向 Windows 开发者与高级用户的本地工具运维工作台。**

核心差异化应是：来源清楚、安装可恢复、进程可控制、失败可诊断、操作有反馈，而不是工具数量最多。

### 9.2 第一阶段：可靠性收束

建议安排未来 1～2 个迭代，具体工期以逐项实现评估为准。

工作内容：

1. 删除与共享目录边界。
2. 进程重复启动、停止重启竞态。
3. 下载去重、可信校验和安装暂存。
4. 配置加载失败保护与凭据策略。
5. 搜索、扫码、离线资产和消息状态修复。

验收标准：

- 重复操作不会损坏状态或安装目录。
- 断网仍能使用已安装工具。
- 停止后任务和资源可确认回收。
- 保存失败不破坏原数据。
- 旧请求不能覆盖新状态。

### 9.3 第二阶段：任务中心与运行中心

统一回答：

- 哪些工具正在运行？
- 哪些下载、安装或系统操作正在进行？
- 哪个操作失败，能否重试？
- 退出 Hanxi 后哪些进程会终止？
- 哪些操作等待用户确认或系统重启？

必须先有统一后台任务模型，再做汇总界面，避免只新增一张页面而不改变底层可靠性。

### 9.4 第三阶段：更新中心与诊断能力

更新中心展示：来源、校验强度、当前及可用版本、用户数据影响、失败恢复方式，以及适用工具的回滚能力。

诊断能力提供默认脱敏的诊断包，包含操作 ID、应用和工具版本、失败阶段、系统环境及必要日志。诊断内容导出和分享应由用户明确控制。

### 9.5 第四阶段：串联已有高频场景

优先组合现有能力：

- 文件搜索 → 快传。
- 环境检查 → 缺失组件安装 → 复检。
- 端口检查 → 进程定位 → 安全终止。
- 工具安装 → 启动 → 日志 → 故障诊断。

随着模块数量增长，可加入统一搜索、收藏和最近使用，降低入口成本。

### 9.6 暂缓方向

- 无明确高频场景的新工具横向扩量。
- 任意第三方插件市场。
- 跨平台扩展。
- 通用包管理器替代品。
- 复制上游软件完整 GUI。
- 没有实测依据的极低内存目标。

## 10. 建议执行顺序

| 批次 | 目标 | 主要范围 | 完成判据 |
| --- | --- | --- | --- |
| 1 | 阻断文件与数据破坏路径 | B01、B02、B05 | 越界拒绝、异常加载不覆盖，专项测试通过 |
| 2 | 收稳进程与安装 | B03、B04、B07、B08 | 并发、失败、停止场景均保持资源和状态一致 |
| 3 | 统一凭据保护 | B06 | 加密失败不降级，运行配置可清理，迁移边界明确 |
| 4 | 修复前端异步与误操作 | B09、F01～F06，验证 F07 | 离线、乱序、关闭、失败和键盘回归通过 |
| 5 | 收敛公共能力与门禁 | 第 6、7、8 章 | 两类代表模块迁移成立，发布验证一致 |
| 6 | 建设运维产品能力 | 第 9 章 | 任务、运行、更新和诊断具有统一可追踪语义 |

上述批次是建议顺序，不是已获批准的实施计划。独立的小修复可以并行，但涉及公共模型的迁移应先验证契约。

## 11. 最终判断

Hanxi 当前不是缺功能，而是需要把已有功能变成用户可以放心依赖的能力。

**下一轮应安排一个明确的可靠性版本，而不是继续以新增工具数量作为主要成果指标。**

本轮分析没有实施修复。后续每项修复应分别记录：触发场景、根因、方案、回归测试、实际验证结果；符合项目规范的踩坑记录再同步进入 `docs/TROUBLESHOOTING.md`，避免把未复现推测写成已发生事故。
