# Hanxi 项目战略与开发路线

> **文档状态**：战略基线  
> **战略周期**：2026-09 至 2027-09  
> **复审周期**：每季度，或重大架构决策后  
> **当前代码基线**：27 个业务模块（10 个自建能力、17 个第三方工具托管）  
> **目标平台**：Windows 10 22H2+ / Windows 11 x64

本文档定义 Hanxi 后续发展的产品边界、目标架构、技术优先级和决策标准。它不是现有文档的重复版本：

- `PRD.md` 描述具体需求与用户工作流；
- `ARCHITECTURE.md` 描述当前已落地的系统结构；
- `DEVPLAN.md` 记录阶段任务和完成状态；
- `TROUBLESHOOTING.md` 沉淀已验证的问题与修复经验；
- **本文档负责决定“为什么做、先做什么、什么不做”。**

当新增工具或功能与本文的产品边界冲突时，应先完成战略评审，而不是先实现再形成既成事实。

## 1. 执行摘要

### 1.1 核心判断

Hanxi 已经完成“验证多种 Windows 工具可以被统一接入”的阶段。当前最主要的矛盾不再是工具数量不足，而是：

1. 模块数量增长快于平台能力沉淀，下载、安装、版本和实例代码存在重复；
2. 架构文档中的“零开销、权限白名单、外部插件”部分领先于真实实现；
3. 安全与发布基线存在明确缺口，继续扩量会放大维护和供应链风险；
4. 用户能进入每个模块，但缺少全局运行、更新、异常和最近任务视角；
5. 前端仍以静态视图表和扁平侧边栏组织模块，接近可维护性上限。

因此，下一阶段应从**工具扩量**转为**平台收束**。

### 1.2 产品定义

> **Hanxi 是面向 Windows 高级用户和开发者的本地工具运维工作台，用一个可信入口管理常用工具的获取、版本、进程、状态和系统集成。**

Hanxi 的目标不是收集更多工具，而是让 Windows 工具的来源、版本、进程和退出行为变得可信且可预期。

### 1.3 核心竞争力

Hanxi 的差异化不在于“内置多少按钮”，而在于以下五项控制能力：

- **可信获取**：来源识别、资产选择、完整性校验、安全解压和隔离安装；
- **可控运行**：JobObject、进程指纹、实例探测、唤窗、优雅退出和强制回收；
- **统一生命周期**：启用、初始化、运行、失败、停用、退出状态可观察；
- **Windows 深度集成**：DPAPI、UAC、注册表、IP Helper、Appx/MSIX、快捷方式；
- **本地优先**：便携数据目录、离线导入、本地配置和可恢复的版本资产。

### 1.4 战略优先级

未来 12 个月的正确顺序是：

1. **P0：安全、构建和生命周期稳定化；**
2. **P1：将托管三件套沉淀为共享托管内核；**
3. **P2：建设全局运行中心、更新中心和统一工作台体验；**
4. **P3：仅在真实需求和安全条件成熟后建设受控扩展生态。**

在 P0 完成前，不以新增托管工具数量作为项目进展指标。除非新工具解决明确的高频场景，或专门用于验证共享内核，否则应暂停横向扩张。

## 2. 当前项目判断

### 2.1 已形成的基础

当前代码已经具备一个优秀 Windows 工具工作台的雏形：

- `internal/app` 是明确的 Composition Root；
- `internal/extapi` 提供统一模块元数据、导航、服务与生命周期契约；
- `internal/modules/<tool>` 采用纵向模块切片，复杂托管工具基本形成 `module + version + instance` 结构；
- `internal/platform/windows` 已沉淀 JobObject、DPAPI、进程指纹、端口/网卡、快捷方式和 Appx 等原语；
- Wails 类型化绑定将 Vue 视图与 Go Service 连接起来；
- 后端测试资产较丰富，当前约有 105 个测试文件，覆盖版本、实例、存储、平台和网络边界；
- CI、Release、便携包和 SHA256 清单已有基本骨架。

其中，**进程治理、版本隔离、Windows 原生能力和便携模式**是最值得继续强化的资产。

### 2.2 当前不是“开放插件系统”

Hanxi 当前准确的架构定义是：

> **模块化单体 + 静态 Wails Service 注册 + 部分运行资源按需激活 + 外部工具托管。**

`LevelExternal`、`Protocol()`、manifest 和 JSON-RPC 仍属于未来预留，不构成可对外承诺的插件运行时。当前存在以下事实：

- 所有模块对象与 Wails Service 在启动时构造和静态注册；
- 模块停用主要隐藏导航并调用 `OnDestroy()`，RPC 路由仍存在；
- 前端所有 Vue View 在 `App.vue` 中静态导入；
- 权限是声明信息，尚未形成调用路径上的强制能力边界；
- 未知外部模块没有动态 UI、签名、安装、升级或崩溃隔离机制。

短期不应为了“插件化”标签过早引入跨进程协议。应先把内部模块契约做实。

### 2.3 “零开销”需要改成可测承诺

目前的懒加载主要减少后台任务、进程、监听器和运行时缓存，并不等于模块对象和前端代码不存在。更准确的目标应是：

- 停用模块无后台 Goroutine、Ticker、网络连接和文件监视器；
- 未激活模块不启动外部进程和主动轮询；
- 未激活模块不持有重型运行时缓存；
- 模块停用后所属句柄和异步任务回归基线；
- 资源数据必须在固定测试环境中测量，而不是使用绝对宣传数字。

`runtime.GC()` 与 `debug.FreeOSMemory()` 是全进程操作，不能替代模块正确关闭资源。是否保留，应由启停性能基准决定。

### 2.4 Windows 专注是产品选择

未来战略周期内继续保持 Windows-only，不以跨平台作为目标：

- JobObject、DPAPI、UAC、注册表和 IP Helper 是产品能力，不是偶然的实现细节；
- 跨平台会迫使项目退化为最小公分母式启动器；
- Go/Vue 可跨平台，不代表产品必须跨平台；
- 非 Windows 代码仅承担编译隔离或测试桩职责，不承诺一致体验。

## 3. 核心用户与关键任务

### 3.1 核心用户

#### Windows 高级用户

需要集中管理便携工具，理解工具从哪里来、装在哪、是否运行、退出 Hanxi 后是否保留，以及如何安全升级或回滚。

#### 开发者与运维型用户

需要网络、端口、开发环境、内网穿透、代理和局域网协作能力；关心多实例、日志、凭据、后台状态和故障定位。

### 3.2 非核心用户

当前不优先服务：

- 只需要应用商店式一键安装的大众用户；
- 需要企业级集中策略和远程设备管理的组织；
- 需要跨平台配置同步的团队；
- 希望运行任意第三方代码插件的扩展开发者。

### 3.3 关键任务类型

| 任务类型 | 典型场景 | Hanxi 应提供的价值 |
|---|---|---|
| 即时诊断 | 释放端口、检查公网 IP、扫描 LAN、检查环境 | 2–3 步得到可操作结果 |
| 持续运行 | frpc、ddns-go、Everything、微信监听、快传 | 全局可见健康状态与退出策略 |
| 工具治理 | 安装、导入、切换、更新、回滚、卸载 | 来源、版本、完整性和数据边界清晰 |
| 本地流转 | 手机投递、Memo、文件搜索与分享 | 形成跨模块工作流，而非孤立页面 |

## 4. 产品边界

| 范围 | 判断 | 说明 |
|---|---|---|
| 工具目录与导航 | 负责 | 分类、搜索、收藏、最近使用、启停与状态 |
| 版本获取与隔离 | 负责 | Release 发现、活动版本、离线导入、回滚 |
| 下载与安装完整性 | 负责 | 官方 digest/签名、哈希、大小、CRC、布局与安全解压 |
| 进程生命周期 | 负责 | JobObject、探测、就绪、唤窗、退出和外部实例区分 |
| Windows 系统能力 | 负责 | DPAPI、UAC、注册表、IP Helper、Appx/MSIX |
| 工具专有业务 UI | 条件负责 | 仅在能形成明显协同或上游缺少适用界面时内嵌 |
| 上游配置修改 | 条件负责 | 必须有公开契约、备份、回滚和风险说明 |
| 成熟上游 GUI 重做 | 不负责 | 不为品牌统一复制完整业务界面 |
| 任意 EXE 启动器 | 不负责 | 不接受没有生命周期和安全契约的快捷方式集合 |
| 通用 Windows 包管理器 | 不负责 | 不与 winget、Scoop、Chocolatey 全面竞争 |
| 恶意代码沙箱 | 不负责 | JobObject 是生命周期治理，不是安全沙箱 |
| 云账户与默认遥测 | 当前不负责 | 维持本地优先；诊断报告由用户主动导出 |
| 跨平台版本 | 当前不负责 | Windows 原语是核心组成部分 |

**硬规则：任何新增能力如果不能归入“工具控制平面”或“Windows 原生工作流”，默认不进入 Hanxi。**

## 5. 能力分层与集成模式

### 5.1 四层能力地图

```text
用户工作台
├─ 工具发现、搜索、收藏、最近使用
├─ 运行中心、更新中心、通知与操作历史
└─ 自建模块专用工作流
        │
应用控制平面
├─ 模块目录与生命周期调度
├─ 调用门、权限、统一错误与操作状态
├─ 配置、Secrets、日志与通知
└─ Wails 类型化命令和事件
        │
模块与托管内核
├─ 自建能力模块
└─ 托管工具适配器
   ├─ Release Source / Asset Selector
   ├─ Download / Verify / Install / Rollback
   └─ Probe / Launch / Ready / Focus / Stop
        │
Windows 平台层
└─ JobObject / DPAPI / Process / Window / Registry / UAC / IP Helper / Appx
```

控制平面负责策略，模块负责业务差异，平台层负责 Windows 原语。模块不应重复实现通用下载事务和进程治理，也不应绕过控制平面直接建立新的高风险能力路径。

### 5.2 三种集成结果

新能力评审后只能进入以下一种模式：

1. **自建模块**：Hanxi 自己实现窄而明确的核心能力；
2. **托管工具**：Hanxi 管理上游二进制的获取、版本和生命周期；
3. **外部链接**：只提供说明或打开官网，不承担安装和运行责任。

“半托管”不能成为默认模式。如果 Hanxi 无法验证资产、判断实例或定义退出语义，就不应在 UI 中表现为已受控工具。

### 5.3 自建模块准则

适合自建的能力应同时满足大部分条件：

- Windows 原生 API 能带来明显优势；
- 功能范围窄、输入输出明确；
- 没有成熟上游，或上游无法形成工作台协同；
- 不需要长期追踪复杂外部 UI；
- 能复用现有平台原语；
- 长期维护成本可控。

### 5.4 托管工具准则

托管模式的原则是：

> 保留上游产品能力，Hanxi 只接管其获取、验证、版本、运行、状态和退出边界。

工具专用代码应集中在这些适配点：

- 如何选择上游资产；
- 如何验证发布者与资产；
- 安装后目录和可执行文件布局；
- 如何判断真正就绪；
- 如何探测外部实例；
- 如何唤窗与优雅退出；
- 配置、缓存和用户数据位于何处。

## 6. 目标架构

### 6.1 总体方向

不建议短期引入 Go Plugin、DLL 或任意代码插件。目标架构应是：

> **模块化单体 + 严格生命周期容器 + 统一工具托管内核 + 安全能力网关。**

```text
Vue 工作台外壳
    │ typed command / event / snapshot
    ▼
Wails 传输适配层
    │ acquire module + validate state + map error
    ▼
应用控制平面
    ├─ Module Catalog
    ├─ Lifecycle Registry
    ├─ Operation Center
    ├─ Permission Gateway
    └─ Secret / Config / Log / Notify
    │
    ├──────── 自建模块
    │
    └──────── 托管工具适配器
                  │
                  ▼
        ArtifactManager + ProcessSupervisor
                  │
                  ▼
             Windows Platform
```

关键变化是：Wails RPC 不再直接成为业务模块的无条件入口，而应先经过模块状态、启用状态、权限和操作追踪检查。

### 6.2 模块生命周期状态机

当前 `Registry.initialized` 与 `Module.IsInitialized()` 存在双重状态源。目标设计只保留 Registry 作为权威状态机：

```text
Disabled
   │ enable
   ▼
Registered
   │ first API / route / background policy
   ▼
Starting ── failure ──► Failed
   │ success               │ retry
   ▼                       │
Active ◄───────────────────┘
   │ disable / shutdown
   ▼
Stopping
   │ resources drained
   ▼
Registered or Disabled
```

生命周期约束：

- `Enable` 表示允许运行，不等于已经初始化；
- 首次 API 调用必须能自动激活，不依赖前端先进入页面；
- 停用时先拒绝新操作，再取消任务，最后等待资源释放；
- 所有后台任务派生自模块级 `context.Context`；
- 禁止长期任务裸用 `context.Background()`；
- 初始化、停用和退出必须串行、幂等并有超时；
- 后台常驻模块通过 `on-demand`、`background-when-enabled` 等显式策略声明，不在 Composition Root 按 ID 写特例。

### 6.3 Wails 调用门

所有模块 API 应通过统一适配层执行：

```text
前端调用
  → 校验模块存在且 Enabled
  → Acquire/Start 模块
  → 校验所需能力与操作策略
  → 创建 operationID 与结构化日志上下文
  → 调用业务服务
  → 标准化错误、通知和终态
```

这解决四个问题：

- 禁用模块仍可被绑定直接调用；
- 生命周期依赖 UI 导航顺序；
- 权限声明没有执行点；
- 各模块错误、日志和进度事件不一致。

### 6.4 共享托管内核

#### ArtifactManager

统一负责：

- Release 来源与缓存；
- 资产筛选和镜像策略；
- 下载超时、重试和取消；
- digest、签名、哈希与大小验证；
- ZipSlip、CRC、布局和解压上限；
- staging、原子安装和失败清理；
- 版本元数据、活动版本、保留和回滚。

#### ProcessSupervisor

统一负责：

- managed / external / detached 所有权；
- JobObject 和进程树；
- stdout/stderr 与状态机；
- readiness probe；
- 外部实例探测；
- 唤窗、优雅退出、宽限期和强杀；
- 跟随 Hanxi 退出与空闲策略。

#### 统一实例状态

```text
not_installed
stopped
starting
running_managed
running_external
running_detached
stopping
failed
```

附加字段至少包括：`ready`、`version`、`pid`、`startedAt`、`lastError`、`ownership` 和 `followOnExit`。

### 6.5 Secret Store

建立统一 Secret Store，Windows 实现使用 DPAPI：

- 配置文件只保存 Secret 引用或密文，不保存明文；
- 前端默认只获取 `hasCredential` 与掩码，不获取完整凭据；
- 新凭据通过替换命令写入；
- 日志、通知、事件和错误同样执行脱敏；
- 至少覆盖 frpc Token/SecretKey、微信凭据和 FileShare 访问口令。

需要明确：DPAPI 绑定 Windows 用户，便携目录复制到另一台机器后不能直接解密。备份功能应默认剔除凭据，或提供用户口令加密导出。

### 6.6 配置与存储

目标配置系统需要：

- `schemaVersion` 与 migration registry；
- 写入失败回滚内存状态；
- 最近成功配置备份与损坏隔离；
- 模块私有配置边界；
- 原子替换和必要的持久化同步；
- Hanxi 数据、版本资产与上游用户数据的明确区分。

### 6.7 前端结构

前端重点不是立即追求运行时插件 UI，而是消除重复接线：

- 引入明确的路由层和异步 View 加载；
- 建立单一模块前端 Catalog，避免 `CORE_VIEWS`、`ROUTE_MODULE_MAP`、首页元数据多处重复；
- 后端负责导航和模块状态，前端负责显式组件 loader；
- 托管工具复用统一控制台、版本管理、状态、错误和确认组件；
- 模块停用时同步释放 KeepAlive 缓存、事件监听和异步任务；
- 建立 typed `useWailsEvent<T>()`，逐步消除事件 `any`；
- 用户始终能区分“Hanxi 托管”“外部启动”“独立运行”。

## 7. 安全与信任模型

### 7.1 必须诚实描述的边界

- JobObject 是进程生命周期治理，不是恶意程序沙箱；
- DPAPI 保护本机落盘凭据，不抵御同一用户上下文内的恶意进程；
- SHA256 只证明内容与可信声明一致；若声明和资产来自同一不可信镜像，则不形成独立信任；
- 便携模式表示数据路径可控，不等于完全不写系统状态；
- UAC 应按具体操作触发，Hanxi 不整体长期运行在管理员权限下。

### 7.2 下载验证等级

| 等级 | 验证方式 | 准入判断 |
|---|---|---|
| A | Authenticode/官方签名或独立官方 SHA256 | 推荐 |
| B | GitHub 官方 digest + 大小 + 解压与布局验证 | 可准入 |
| C | 只有大小、CRC、MD5/SHA-1、版本资源或布局自检 | 条件准入，UI 必须披露风险 |
| D | 无稳定来源、无法验证、动态安装器内容不可控 | 拒绝托管 |

镜像只作为传输来源，不作为完整性信任根。验证等级 C 不得在文档中描述为“可信验证完成”。

### 7.3 当前 P0 安全问题

以下问题应进入修复队列，而不是继续停留在文档提示：

1. FileShare `AuthToken` 尚未形成服务端认证，且监听面、CORS、上传和路径边界需要安全收敛；
2. 微信 Token/ContextToken 尚未统一进入 DPAPI Secret Store，且不应完整返回前端；
3. frpc 需覆盖 SecretKey、加密失败 fail-closed、临时 TOML 全生命周期清理和权限收紧；
4. UAC 端口查杀 helper 应携带并重新验证完整进程指纹，而不是只接收 PID；
5. 权限声明尚未形成宿主强制调用门；
6. 日志脱敏需同时按属性 key、嵌套结构和事件载荷处理；
7. 缺少官方强校验的工具，不应把“自哈希、大小或 CRC”表述成真实性验证。

## 8. 工程与发布治理

### 8.1 当前最高优先级

- `go.mod` 使用 Go 1.26，而 CI/Release 使用 Go 1.24，必须统一；
- Wails Go 库固定 beta.10，但 CLI 与前端 Runtime 存在 `latest` 浮动，应固定完整工具链；
- CI 仅手动触发，没有 `push` / `pull_request` 门禁；
- Release 未先运行完整测试，手工发布 tag 选择逻辑存在发布错误风险；
- 版本号散落在产品常量、构建配置、PE、NSIS、MSIX 和 workflow，应建立单一版本源并校验；
- Release 仅发布同渠道 SHA256，缺少 Authenticode、SBOM 和 provenance；
- 构建流程会执行 `go mod tidy` 并重写 bindings，应改为独立 drift check，生产构建不修改源码树；
- 前端没有自动化测试，当前只有类型检查和构建。

### 8.2 建议质量门

每个 PR 至少自动执行：

1. `gofmt` / `go vet` / `go test -race`；
2. 前端类型检查、构建、单元测试；
3. bindings 与依赖文件漂移检查；
4. `govulncheck` 与依赖安全扫描；
5. Windows 生产构建；
6. 模块元数据与文档清单一致性检查。

每个 Release 必须额外执行：

- tag、产品版本、PE/包元数据一致性校验；
- 完整 CI；
- 便携包 smoke test；
- 资产签名和 SHA256；
- 可追溯构建信息、SBOM 与发布说明；
- 重复发布并发保护。

## 9. 路线图

### P0：稳定控制面（0–6 周）

**目标**：在继续扩充工具前，把安全、构建、生命周期和供应链底线变成可验证契约。

主要交付：

- 统一 Go、Wails CLI、Runtime、Node 和构建工具版本；
- CI 变为 PR/push 自动门禁，Release 依赖完整测试；
- 修复发布 tag 和版本单一来源问题；
- Secret Store 覆盖微信、frpc 与 FileShare；
- FileShare 建立认证、安全默认值、请求限制和 reparse point 边界；
- UAC helper 重新验证完整进程指纹；
- extapi 采用唯一生命周期状态源和模块级 Context；
- 模块 API 建立 Enabled/Acquire 调用门；
- 定义下载验证等级与 fail-closed 底线；
- 补齐日志保留、流式尾读和结构化脱敏；
- 建立启动、空闲、启停、退出和孤儿进程基准。

**退出条件**：

- PR 和 tag 均不能绕过自动质量门；
- 明文敏感凭据落盘为 0；
- FileShare 未认证访问被拒绝；
- 正常/异常退出后的 Hanxi 托管孤儿进程为 0；
- 模块停用后无所属后台任务、连接和句柄；
- 文档中的权限、懒加载和验证能力与实际实现一致。

### P1：托管工具平台化（6–16 周）

**目标**：从“每接一个工具复制一套实现”转为“共享内核 + 工具适配器”。

主要交付：

- ArtifactManager：Release、下载、验证、解压、staging、安装、回滚；
- ProcessSupervisor：Job、状态、探测、唤窗、退出和所有权；
- 统一实例状态、Operation、事件信封和错误码；
- 统一活动版本、导入、卸载、回滚与数据保留契约；
- 建立托管工具契约测试套件；
- 先迁移三类代表模块，再迁移其余模块；
- 提供新托管工具适配模板和准入证据模板。

**退出条件**：

- 普通托管工具至少 70% 的逻辑来自共享包；
- 新工具不再复制下载、解压和 JobObject 主流程；
- 安装中断不会破坏现有可运行版本；
- 所有托管工具通过同一套生命周期和供应链契约测试；
- 上游特殊性只存在于明确适配器中。

### P2：完整工作台体验（16–28 周）

**目标**：从多个模块页面升级为用户能理解整个工作区的运维工作台。

主要交付：

- 分类导航、工具搜索、收藏与最近使用；
- 首页聚合“正在运行、需要处理、最近任务、常用入口”；
- 全局运行中心：版本、PID、健康、所有权、运行时长和退出策略；
- 全局更新中心：可用更新、验证等级、批量下载、失败重试和回滚；
- 统一托管控制台、版本管理、确认框、路径选择器和错误面板；
- Vue Router/路由层、异步 View、typed event composable；
- 前端 Vitest + Vue Test Utils，关键桌面流程增加 E2E；
- 配置备份、恢复、迁移和诊断报告导出；
- 至少三条跨模块工作流。

**退出条件**：

- 用户不进入各模块也能发现运行异常和待更新项；
- 任意工具最多两次导航操作可达；
- 所有破坏性操作使用统一确认并说明影响范围；
- 主要页面在 760px 宽度下可完成核心任务；
- 每个失败状态提供明确下一步操作；
- 新模块不再要求维护多套 route/icon 元数据。

### P3：受控扩展生态（28–52 周）

**目标**：在内建契约稳定后，先建设声明式工具托管，再决定是否开放代码插件。

主要交付：

- 声明式 Tool Manifest；
- 资产、验证、安装、启动、探测和退出策略声明；
- 宿主生成统一控制台；
- Manifest 静态校验、签名和兼容性版本；
- 官方工具目录；
- 若存在至少三个声明式能力无法满足的真实需求，再设计 JSON-RPC 子进程插件；
- 外部插件必须具备权限授权、能力 Token、JobObject、崩溃隔离和回滚。

**启动前置条件**：

- 内建模块契约至少稳定两个版本；
- 权限能由宿主强制执行；
- 插件来源、签名和撤回机制明确；
- 插件崩溃不影响宿主；
- 至少有三个真实外部扩展需求；
- 维护者能够承担协议兼容成本。

## 11. 新工具准入标准

### 11.1 一票否决

存在任一情况时，不进入托管模式：

- 许可证不明确，或不允许当前获取/展示方式；
- 没有稳定的 Windows x64 资产；
- 必须通过不可控在线安装器获取，且无法验证最终内容；
- 必须让 Hanxi 整体长期管理员运行；
- 涉及驱动、系统服务或高风险全局钩子，但项目没有对应治理能力；
- 无法判断进程是否真正启动；
- 无法定义退出语义，且强杀可能破坏用户数据；
- 自带更新器无法关闭，会绕过 Hanxi 版本管理；
- 上游停止维护且存在未解决的高危漏洞；
- 与现有工具高度重叠，没有明显价值增量；
- 无法向用户说明网络行为、数据目录和隐私边界。

### 11.2 100 分评分模型

| 维度 | 分值 | 核心问题 |
|---|---:|---|
| 用户价值 | 25 | 是否解决明确、高频、可重复的 Windows 任务 |
| 战略匹配 | 20 | 是否加强工具控制平面或 Windows 工作流 |
| 供应链与安全 | 20 | 是否有稳定来源、digest/签名和清晰许可证 |
| 可托管性 | 15 | 能否探测、启动、就绪、唤窗、退出和回收 |
| 维护成本 | 10 | 上游变化频率与适配复杂度是否可控 |
| 工作台体验 | 10 | 是否能形成清晰入口且不过度重复 |

- `≥ 80`：可以进入计划；
- `70–79`：条件准入，必须完成架构评审；
- `< 70`：拒绝；
- 命中一票否决：无论总分多少均拒绝。

### 11.3 准入证据包

实现前必须提供：

1. 上游仓库、官网和许可证；
2. 最近三个 Release 的资产稳定性；
3. Windows x64 资产筛选规则；
4. digest、签名或降级验证方式；
5. 安装目录与可执行文件布局；
6. 配置、缓存与用户数据位置；
7. 自带更新器行为；
8. 单实例、互斥体、窗口或进程探测依据；
9. 启动就绪条件；
10. 唤窗与优雅退出方式；
11. JobObject 与子进程兼容性；
12. 管理员权限、服务、驱动和网络行为；
13. 外部实例处理规则；
14. 本地导入、卸载和回滚规则；
15. 用户可见风险说明。

证据必须来自源码、官方文档、API 或真机验证，不能只根据文件名和窗口表现猜测。

### 11.4 完成定义

只有满足以下条件才算“已集成”：

- 可发现或导入版本；
- 资产执行对应等级的验证；
- 安装有 staging、失败清理和旧版本保护；
- 活动版本可确定；
- 启动和就绪状态可观察；
- managed、external、detached 可区分；
- 唤窗和退出经过真机验证；
- 运行版本不能被误卸载；
- 错误包含可执行修复建议；
- 许可证和第三方声明已更新；
- 生命周期、版本、实例与失败路径测试通过；
- 真机验收清单完成。

只有“下载”和“启动”按钮不算完成。

## 14. 文档治理

权威关系：

- 产品边界和长期取舍：`PROJECT_STRATEGY.md`；
- 当前实现事实：`ARCHITECTURE.md`；
- 具体需求：`PRD.md`；
- 当前任务和里程碑：`DEVPLAN.md`；
- 已验证技术问题：`TROUBLESHOOTING.md`。

以下变化必须复审本文并记录 ADR：

- 改变 Windows-only 定位；
- 引入外部插件、云账户或同步；
- 支持驱动或系统服务；
- 改变托管工具默认退出策略；
- 新工具突破一票否决条件；
- 模块权限模型或进程所有权模型发生变化；
- Wails、Go 或 Windows 平台基线发生重大变化。

每个 ADR 至少记录背景、方案、最终判断、未选方案、风险和复审条件。
