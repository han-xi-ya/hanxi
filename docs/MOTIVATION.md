# 为什么做 Hanxi(缘起与动机)

> **文档状态**：项目缘起自述
> **更新日期**：2026-09-18
> **分工**：本文回答"**为什么会想做这个软件**"；`PROJECT_STRATEGY.md` 回答"做什么、不做什么"，`PRD.md` 回答"做成什么样"。三者互补，未来功能取舍拿不准时，以本文的场景为原始依据。

## 1. 我的背景

Go 程序员，电脑重度使用者。经常换电脑，偶尔临时使用别人的电脑，也经历过重装系统。每次换环境，都要从零面对同一类问题：**这台电脑上什么都没有，而我明天就要用它干活。**

## 2. 具体痛点

1. **新环境一片空白**：换机/重装后要逐个搜索、下载、安装、配置常用软件；浏览器搜索结果里充斥广告站、捆绑下载器和假下载按钮，"下载"这个动作本身就是风险。
2. **好工具找不到**：GitHub 上有很多好用且开源免费的工具，"我知道有这么个东西"和"我现在马上能找到它"是两回事，每次都要重新搜索、重新甄别。
3. **临时使用成本高**：不少软件可能只用一次，装完再卸载麻烦，还担心留下残余、拖慢系统。
4. **账号与设备限制**：之前常用 Quicker 的指尖工具，真正离不开的只有截图、贴图、OCR 三样——但它要求账号登录且限制设备数量，换电脑本身就成为麻烦。
5. **临时机器上的隐私残留**：在别人电脑上想传个文件，微信"文件传输助手"最顺手；但一登录微信，账号痕迹和聊天数据就留在了那台不属于我的机器上。
6. **环境说不清**：一台电脑装过什么、什么版本、有没有中过"全家桶"，时间久了完全摸不清楚，排查问题像考古。

## 3. 我的解法

一句话：**把我认可的工具和我自己的数据，收进一个可携带、可同步、来源可信的环境里。**

- **托管开源便携软件**：从 GitHub 挑选好用、开源免费的工具，统一做版本管理、完整性校验、进程启停监管。接手新电脑后，不用再搜索"XX 软件 下载"——打开 Hanxi，在里面找就行；来源、版本、哈希都在 catalog 里管着。
- **绿色便携 + 集中数据目录**：程序和它的数据收在明确的目录结构里，不摊到系统各处。
- **NAS 同步 = 软件随身**：计划用飞牛（fnOS）的同步软件，把 Hanxi 程序目录与数据目录整包同步。到任何一台电脑同步回来，等价于**这些软件装在了 NAS 里**，随取随用。
- **自建高频刚需**：截图、贴图、OCR（替代 Quicker 的三样刚需，不受账号和设备数限制）、局域网文件快传、微信机器人/文件助手（临时传文件不用登录微信，不给别人的电脑留痕迹）——这类"一登录就留数据"的能力自己做，用完就走。
- **持续纳管**：以后继续在 GitHub 上发现、评估有价值的好用软件，逐步托管进来；Hanxi 同时是这些选择的清单和容器。

## 4. 接手一台新电脑时的期望流程

1. 拿到 Hanxi（拷贝目录，或让飞牛同步指向既有目录）；
2. 托管工具首次使用时按需下载（红线不变：仓库与安装包不捆绑第三方二进制，下载源由受控目录管理）；
3. 日常刚需（截图/贴图/OCR/传文件/扫描诊断）当场可用；
4. 全程不需要：百度搜下载、注册账号、登录微信、装卸载一次性软件。

已知边界：DPAPI 加密的凭据绑定本机登录用户，**同步不随附密钥/凭据**，换机后涉及凭据的模块（如 frpc Token）需重新录入——这是安全设计使然，不是缺陷。

## 5. 为谁做、做到什么程度

- 这是**业余时间开发的自用项目**，第一个、也是最重要的用户是我自己；功能优先级以我的真实场景为准，不为假想用户提前建设。
- **可以开源、欢迎别人用**，但那是顺带的收益，不是投入的前提。
- 由此决定的架构口味：**便携、可同步、来源可信、退出无残留**，比"功能数量多"更重要。
