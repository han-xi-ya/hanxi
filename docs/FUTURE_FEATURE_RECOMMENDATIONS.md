# Hanxi 后续功能建议

> **文档状态**：候选方向评估，不代表已排期或承诺实施  
> **评估日期**：2026-09-19  
> **适用基线**：当前 `dev` 分支、41 个业务模块、Wave 0–5 已完成  
> **决策原则**：优先服务作者本人“Windows 重度使用 + 经常换机/重装 + 飞牛 NAS 同步 Hanxi 整体目录”的真实场景。

## 1. 结论

Hanxi 现阶段**不缺更多工具，缺的是让现有工具和数据真正做到可搬、可查、可恢复、可更新**。

当前已经具备模块 Catalog、逻辑安装态、统一调用门、Operation、ArtifactManager、ProcessSupervisor、更新感知、历史版本、快照、MCP，以及 41 个业务模块。继续横向接入同类工具，边际收益已经明显低于完善数据面和全局治理能力。

建议后续主线按以下顺序推进：

1. **先补“软件装在 NAS”最后一公里**：安全换家、数据边界体检、Secret Store；
2. **再补统一治理闭环**：更新中心、数据根健康、诊断中心、运行中心；
3. **最后改善灾备与日常维护**：灾备包、配置备份适配器、本体自更新、固定维护策略；
4. 只有能显著强化 Windows 工作流、且不与现有托管工具重叠的新能力，才考虑进入候选池。

---

## 2. 产品现状与判断依据

### 2.1 产品定位

Hanxi 的核心目标不是收集尽可能多的软件，而是：

> 把认可的工具和自己的数据，收进一个可携带、可同步、来源可信、退出无残留的 Windows 环境。

真实黄金路径是：将 Hanxi 程序和数据目录通过 NAS 同步到另一台电脑，按需获取托管工具后立即恢复工作，不再搜索下载、不依赖账号、不反复安装卸载。

因此，以下能力比继续增加工具数量更重要：

- 数据是否真的都随 Hanxi 根目录同行；
- 搬家和换绑时是否会复制不完整或带着运行中进程；
- NAS 离线、空间不足、同步冲突时是否会继续写坏数据；
- 凭据、快照和灾备包是否有清晰的敏感数据边界；
- 已发现的工具更新能否统一执行、失败回滚；
- 换机后哪些内容可直接复用、哪些必须重新填写，是否能明确告知。

### 2.2 当前能力基线

当前代码实际注册最多 **41 个业务模块**，已经覆盖：

- 网络诊断、端口、局域网、文件快传、frpc、DDNS、远控；
- 环境和软件版本检测、卸载、监控、启动盘、磁盘管理；
- 桌面标注、右键轮盘、按键显示、图片查看、留言板；
- 随手记、Everything、OCR、微信机器人、网页应用、Snipaste；
- 录屏、图片压缩和媒体下载；
- VS Code、CC Switch、Paseo 和完整 WSL 工作台；
- 模块中心、首页、托盘、主题、历史、快照、AI/MCP 接入。

Wave 5 已完成版本面 20 家、instance 面 18 家的共享内核委托，以及托管控制台 20/20 页面收敛。现阶段继续增加同质托管工具，会重新扩大维护面，而不是补齐产品主价值。

### 2.3 已有但尚未闭环的能力

以下不是“从零新增”，而是现有平台能力的最后一公里：

- 已有统一更新感知，但没有全局批量更新、失败回滚和统一保留策略；
- 已有运行状态摘要和单模块实例控制，但没有完整的跨模块运行治理中心；
- 已有历史版本和快照，但还不是可跨机导入、可预检的灾备包；
- 已有同级数据根和 `hanxi.bind`，但换绑仍要求用户手工搬运数据；
- 已有 DPAPI 原语，但部分敏感配置仍混在普通配置中；
- 已有模块治理能力，但不少上游工具的数据仍落在 `%APPDATA%`、用户目录或系统状态中；
- F1–F9 已合并，但换机、OCR、WSL USB、多 DPI、热键和 MCP 客户端等仍有真机验收债。

## 3. 推荐功能优先级

## P0：直接强化核心定位

### 3.1 安全换家 / NAS 同步前收口 / 搬家向导

**建议：最先做。**  
**收益：极高** ｜ **复杂度：中**

#### 现状问题

存储设置可以修改绑定位置，但数据复制仍由用户手工完成。运行中的托管实例、WebView 缓存、版本元数据、Operation journal 或同步软件都可能让“直接复制整个目录”得到不一致副本。

#### 建议功能

提供两种明确模式：

1. **复制后切换**：Hanxi 负责将当前数据根安全复制到新位置；
2. **绑定已有副本**：验证目标目录完整后，仅切换 `hanxi.bind`。

标准流程：

1. 检查目标路径是否存在、可写、空间足够；
2. 识别本地盘、UNC/NAS、同步目录及原子替换能力；
3. 列出仍在运行的托管实例和未完成 Operation；
4. 停止或要求用户处理相关实例；
5. 立即创建 checkpoint；
6. 复制到 staging，而不是直接覆盖目标；
7. 对关键 JSON、receipt、journal 和文件摘要做校验；
8. 生成可回滚 receipt；
9. 原子切换绑定；
10. 重启后复验，失败则提供恢复旧绑定入口。

还可增加“**准备同步/安全退出**”操作：暂停会产生持续写入的模块，执行 checkpoint，确认没有活动写事务后再提示同步软件接管。

#### 验收重点

- 数据源和目标目录相同、嵌套或循环链接时必须拒绝；
- NAS 中途离线、空间不足、文件被占用时不得留下已切换但不完整的绑定；
- 不覆盖未经确认的既有完整目录；
- DPAPI 凭据要明确提示“文件会同行，但换机后可能无法解密”。

---

### 3.2 模块数据边界清单与“可迁移性体检”

**收益：极高** ｜ **复杂度：中**

#### 现状问题

“同步 Hanxi 整体目录”并不等于所有托管软件状态都会同行。当前部分工具的配置和用户数据仍保存在 Windows 用户目录，例如 `%APPDATA%`、`%USERPROFILE%` 或工具自有目录中。

如果界面不明确说明，用户很容易把“版本资产能同步”误解成“所有软件配置都能同步”。

#### 建议模型

为每个模块登记 `DataFootprint`：

| 类型 | 示例 | 迁移语义 |
|---|---|---|
| `binary` | 托管版本资产 | 通常随 Hanxi 数据根同行 |
| `config` | 工具配置 | 可能在 Hanxi 根，也可能在 `%APPDATA%` |
| `user-data` | 用户内容、数据库 | 需明确是否纳入备份 |
| `cache` | WebView、缩略图、临时文件 | 默认不迁移 |
| `system-state` | 注册表、自启、防火墙、驱动 | 不能靠目录同步恢复 |
| `credential` | Token、密码、登录态 | DPAPI 密文可同行，但跨机通常需重填 |

#### 用户界面

在“存储目录”或独立“可迁移性体检”中展示：

- 完全随行；
- 部分随行；
- 留在当前 Windows 用户目录；
- 系统安装态；
- 凭据需在新机器重填；
- 当前路径不存在、不可读或体积异常。

第一阶段只做**只读盘点和报告导出**，不要一开始就试图接管全部上游配置。第二阶段再为最有价值、数据契约稳定的工具增加备份适配器。

---

### 3.3 统一 Secret Store 与快照敏感数据分层

**收益：极高** ｜ **复杂度：中**

#### 目标

把 Token、密码、代理凭据等从普通配置字段中分离，统一通过 `SecretRef + DPAPI` 管理。

#### 建议范围

- 微信 BotToken、ContextToken；
- frpc SecretKey、代理凭据；
- FileShare 密码；
- 后续模块新增的账号凭据。

#### 交互原则

- 前端只读取 `hasSecret`、掩码和更新时间，不回传明文；
- 修改时区分“保持原值”“替换”“清除”；
- DPAPI 解密失败时明确提示疑似更换电脑或 Windows 用户；
- 历史版本和灾备包区分：
  - 普通配置；
  - DPAPI 密文；
  - 用户内容；
- 跨机导入后列出必须重新填写的凭据。

#### 明确不做

不建设可迁移主密钥或云端密钥同步。DPAPI 本机绑定是既定安全属性，不应为了“无感搬家”削弱边界。

## P1：补齐平台治理闭环

### 3.4 统一更新中心

**收益：高** ｜ **复杂度：中高**

#### 现状

当前已经能发现更新、展示 `update-available`，但统一控制面主要停留在“看见有更新”。更新执行仍分散在模块页面，缺少批量确认、统一失败重试和回滚入口。

#### 建议功能

- 按模块、分组或全部选择更新；
- 展示当前版本、目标版本、来源、摘要验证等级和预计空间；
- 更新前自动 checkpoint；
- 停止受影响实例；
- 下载、摘要验证、staging、切换 active；
- 启动健康探针；
- 失败自动切回旧版本；
- 统一 Operation 进度与错误；
- 设置每个工具保留最近 N 个版本、全局空间上限和固定版本保护。

#### 产品取舍

建议“自动检测、用户批量确认”，不建议无人值守自动安装。个人工作台更需要可控和可回滚，而不是追求后台全自动。

#### 前置技术债

统一更新/恢复前，应核对所有托管版本树是否都注册进启动恢复链，不能只覆盖少数模块。

---

### 3.5 DataRootHealth：数据根与 NAS 健康保护

**收益：高** ｜ **复杂度：中**

#### 建议检测项

- online / writable；
- 剩余空间；
- 本地盘、网络共享或同步目录；
- volume identity；
- 目录延迟；
- 原子 rename 能力；
- 云盘 placeholder / 文件未落地；
- 常见同步冲突副本；
- 数据根是否被错误嵌套或重复绑定。

#### 保护策略

当 NAS 不在线、数据根只读、关键文件未完整同步或空间不足时，进入**受限写模式**：

- 允许浏览状态和打开不写数据的模块；
- 阻止安装、卸载、恢复、迁移、版本切换等高风险写操作；
- 给出明确原因和“重新检测”入口；
- 不静默改回其他数据目录。

检测应发生在启动、恢复焦点和写事务前，不应持续高频扫描整个数据树。

---

### 3.6 诊断与自愈中心

**收益：高** ｜ **复杂度：中**

将当前分散在首页、Operation、通知、模块页和设置中的异常统一汇总：

- 数据根/NAS 异常；
- 快照失败或长期未成功；
- 更新检查失败；
- 未收口 journal；
- 版本树 meta 或 active pointer 异常；
- 外部实例和残留进程；
- 自启路径漂移；
- MCP 配置冲突或授权拒绝；
- DPAPI 解密失败；
- 托管工具数据目录不随行；
- 关键真机验收尚未通过。

每项只提供可解释的操作：重新检测、打开目录、停止实例、恢复旧版本、重新填写凭据、导出诊断包。不要做不可解释的“一键修复全部”。

诊断包应默认脱敏，只在用户显式操作时导出。

---

### 3.7 全局运行中心

**收益：高** ｜ **复杂度：中**

当前已有首页运行摘要、模块中心运行筛选和 ProcessSupervisor，适合进一步形成跨模块运行视角。

建议展示：

- 模块与实例名；
- PID、运行时长、可执行路径；
- 当前版本；
- managed / external / detached 所有权；
- 跟随 Hanxi 退出策略；
- 就绪、异常、退出中状态；
- 唤窗、打开日志、停止；
- 多实例、残留实例和版本路径漂移。

它与模块中心的区别是：模块中心回答“有哪些能力和是否安装”，运行中心回答“现在到底有什么进程在跑、由谁管理、退出时会怎样”。

外部实例强杀属于高风险扩展，应继续遵守既有 Wave 4X 裁决：没有作者明确授权，不默认扩大控制范围。

---

## P2：灾备、维护与系统集成

### 3.8 显式灾备包导入/导出

**收益：高** ｜ **复杂度：中**

历史版本解决“本机误改后的恢复”，灾备包解决“换机、重装或目录损坏后的重建”。两者不应混为一套语义。

建议使用 `.hanxibackup`（ZIP + manifest）并提供档位：

- **A：轻量配置包**：Hanxi 配置、模块安装态、非敏感偏好；
- **B：完整用户包**：A + Memo、Operation/receipt、MCP 授权等；
- **C：离线资产包**：B + 选定托管版本资产，体积可能很大。

导入前 dry-run，明确展示：

- 将创建、覆盖、跳过哪些文件；
- 哪些 DPAPI 密文跨机不可解；
- 哪些上游工具配置不在包内；
- 需要多少空间；
- 恢复后需要重启哪些模块。

恢复前自动拍 checkpoint，不直接覆盖正在使用的数据根。

---

### 3.9 托管工具配置备份适配器

**收益：中高** ｜ **复杂度：按工具递增**

这是 `DataFootprint` 的第二阶段，不应先于数据边界清单建设。

首批可考虑：

1. ddns-go；
2. Paseo；
3. RustDesk / SubnetDesk；
4. PicLite；
5. Keyviz。

每个适配器都必须有明确契约：

- 官方或稳定的数据目录；
- 停止实例后复制；
- 排除 cache、日志和 WebView2 临时数据；
- manifest 与摘要校验；
- 恢复前备份原目录；
- 恢复失败可以回滚；
- 不把登录态“能复制”误报为“跨机一定有效”。

不要做一个扫描 `%APPDATA%` 后全部打包的通用方案，这会制造敏感数据、锁文件和不可验证恢复问题。

---

### 3.10 Hanxi 本体自更新

**收益：中高** ｜ **复杂度：中高**

本体更新适合进入后续阶段，但应保持克制：

1. 从官方 GitHub Release 检查版本；
2. 下载到程序同级 staging；
3. 校验 HTTPS 来源和官方 SHA-256；
4. 退出 Hanxi；
5. 由最小 helper 原子替换；
6. 启动新版本并验证；
7. 失败恢复旧 exe。

不需要为个人自用场景重建 Catalog PKI、密钥轮换、灰度渠道和撤回系统。若没有 Authenticode，界面应诚实说明信任来源是 HTTPS、官方 Release 和 checksum。

#### 实施前必须先修正文档/发布流水线漂移

当前发布说明仍残留旧“`hanxidata` 是便携模式标记、否则使用 `%APPDATA%`、兼容旧 `data/`”语义，而现行策略已是 exe 同级数据根 + `hanxi.bind`。本体更新开始前必须先统一这部分事实，否则会直接误导搬家和恢复操作。

---

### 3.11 固定维护策略

**收益：中高** ｜ **复杂度：中**

只提供少量经过验证的 recipe：

- 启动后检查数据根/NAS；
- 延迟检查工具更新；
- 空闲时清理下载残件、旧日志和超额旧版本；
- 退出前 checkpoint；
- NAS 恢复在线后提醒；
- 长期未成功快照时提醒；
- 自启路径漂移时修复或提示。

每项需要独立开关、上次执行结果、下次执行时间和失败原因。

不要演进成通用 cron 或 Windows Task Scheduler 管理器；这会扩大权限与误执行风险，也超出 Hanxi 产品边界。

---

### 3.12 轻量 Windows 集成补强

**收益：中** ｜ **复杂度：低至中**

可考虑：

- `hanxi://` 协议：打开指定模块、定位 Operation、导入受支持的分享数据；
- SendTo：发送到 Hanxi 快传、随手记或 OCR；
- 自启路径体检：程序搬家后识别并修复 HKCU Run 的旧路径；
- 正规 Start Menu shortcut / AUMID：改善 Toast 归属；
- WSL 快速入口：终端、VS Code、资源管理器和自定义工作目录。

不建议开发 Explorer Shell Extension DLL。协议、SendTo 和快捷方式已经能覆盖主要价值，原生扩展会引入崩溃、残留、签名和升级成本。

---

### 3.13 AI 接入审计

**收益：中** ｜ **复杂度：低至中**

保持 MCP 工具只读和逐项授权边界，同时增加本地可见性：

- 客户端标识；
- 工具名；
- 调用时间和耗时；
- 返回条数、是否截断；
- 成功、离线、未授权等结果；
- 最近调用列表；
- 一键撤销单项授权。

审计记录不保存查询正文、OCR 文本、Memo 正文或完整本地路径，以免“为了审计再次复制敏感内容”。

CLI `--list` / `--call` 可作为后续脚本桥，但优先级低于审计和三客户端真机验收。

---

## P3：有明确真实需求后再做

### 3.14 多机配置档案，而非实时双向同步

**收益：中** ｜ **复杂度：中高**

如果未来确实在多台电脑间长期使用，可提供“机器档案”：

- 模块启用状态；
- 托盘菜单；
- WebApp 条目；
- 非敏感偏好；
- 机器名、能力和最后使用时间；
- 需重新填写的凭据清单。

不建议对运行中的 `config.json` 做通用双向实时合并。两台机器同时写入时会遇到 last-writer-wins、语义冲突和同步工具产生的冲突副本。对个人自用项目，显式导出/应用档案更可靠。

### 3.15 原生截图/贴图闭环

截图和贴图当前由 Snipaste 提供，不能因为 MOTIVATION 中提到“自建高频刚需”就重复造一个普通截图工具。

只有当原生实现能形成下列明显差异时，才值得立项：

- 截图后直接 OCR；
- 一键进入 Memo 或 FileShare；
- 与历史记录、敏感遮罩、悬浮卡统一；
- 不依赖外部登录和数据目录；
- 相比 Snipaste 真正减少操作步骤。

否则继续托管 Snipaste 更符合当前战略。

## 4. 推荐实施路线

### 第一阶段：搬家与数据真相

1. 安全换家 / 同步前收口；
2. `DataFootprint` 和可迁移性体检；
3. 统一 Secret Store；
4. 完成 F6、F3、F4、F7、F9 等现有真机验收；
5. 修正数据根和模块数量相关文档漂移。

**阶段结果**：用户第一次能够明确知道“哪些会随 NAS 同行、哪些不会”，并能安全完成数据根切换。

### 第二阶段：统一治理

1. 统一更新中心；
2. DataRootHealth 和 NAS 离线保护；
3. 诊断与自愈中心；
4. 全局运行中心；
5. 对 LAN、PortScan 等文案与实现差异做真实性审计。

**阶段结果**：现有共享内核真正转化为用户可见的跨模块控制面。

### 第三阶段：灾备与恢复

1. `.hanxibackup` 灾备包；
2. 首批 3–5 个配置备份适配器；
3. 本体自更新；
4. 版本资产空间治理；
5. 自启和系统集成漂移检查。

**阶段结果**：换机、重装和目录损坏时有明确、可验证的恢复路径。

### 第四阶段：低成本体验增强

1. 固定维护策略；
2. `hanxi://`、SendTo、正规通知身份；
3. AI 调用审计；
4. 按真实使用频率选择 WSL 快速入口等窄功能。

## 5. 不建议投入的方向

### 5.1 继续大量接入同质桌面工具

已有 41 个模块和 25 款第三方托管工具。除非解决明确高频场景或验证新的平台能力，否则继续扩量只会增加上游变更、下载解析、退出语义和测试维护成本。

### 5.2 通用 Windows 包管理器

不与 winget、Scoop、Chocolatey 竞争。Hanxi 的价值是精选工具的可信获取、生命周期和 Windows 深度集成，不是覆盖任意软件。

### 5.3 开放插件市场或任意代码插件

当前准确形态是模块化单体，不应为了“插件化”标签引入动态 DLL、任意 Go 插件或跨进程运行时。声明式 manifest 和签名 Catalog 已从默认路线裁掉。

### 5.4 自建 Catalog PKI、密钥轮换和撤回体系

个人自用、NAS 同步场景下投入与收益不匹配。保持 HTTPS + 上游官方摘要必检，并在真实外部分发出现后再重新评审。

### 5.5 可迁移 DPAPI 主密钥

不要为了跨机无感恢复弱化本机用户绑定。正确体验是识别解密失败并列出需重填凭据。

### 5.6 自动把快照推到 GitHub/GitLab

快照应继续保持“永不自动 push”。远端同步交给用户明确配置的 NAS/同步软件；Hanxi 负责健康检查、显式灾备包和恢复预检。

### 5.7 通用计划任务、Shell Extension、驱动或常驻系统服务

这些方向显著扩大提权、残留、崩溃和升级治理面。固定维护 recipe、协议链接和 SendTo 已足够覆盖主要个人场景。

### 5.8 云账户、默认遥测、服务器端同步和跨平台

均偏离“本地优先、Windows 原生、个人自用”的产品定义。Windows JobObject、DPAPI、UAC、注册表等是能力，不是等待抽象掉的技术债。

### 5.9 全量备份 cache、logs、runtime 和 WebView2 数据

这类目录体积大、锁文件多、含敏感残留且恢复价值低。应通过 manifest 分档选择真正有恢复价值的配置、用户数据和版本资产。

## 6. 在新增功能前应先处理的事实漂移

以下问题会直接影响路线判断，建议作为文档维护任务先收口：

1. README、PRD、PROJECT_STRATEGY 等仍有 **37/38 模块**旧统计，当前代码实际为 **41 个**；
2. 部分文档仍描述 `hanxidata` 标记、`%APPDATA%` 回退和旧 `data/` 兼容，已与现行“exe 同级 + `hanxi.bind`”策略冲突；
3. Release workflow 的便携说明仍包含旧路径语义；
4. BACKLOG 中 WebApp 状态落后于当前注册和导航事实；
5. 个别模块可能存在对外文案超出真实实现的情况，应先选择“补实现”或“降文案”，而不是把它们误判为全新功能。

这些漂移不只是文字问题：它们会误导 NAS 搬家、发布包使用和后续自更新设计。

## 7. 功能准入检查表

以后评估新功能时，建议依次回答：

1. 是否解决作者本人当前真实、重复发生的问题？
2. 是否属于工具控制平面或 Windows 原生工作流？
3. 是否与现有 41 个模块或托管上游明显重复？
4. 是否强化“便携、可同步、来源可信、退出无残留”？
5. 数据、凭据、进程和卸载边界是否可解释？
6. 能否复用 ArtifactManager、ProcessSupervisor、Operation、历史和快照？
7. 是否需要长期跟踪不稳定的上游私有格式？
8. 是否增加提权、系统残留、供应链或隐私风险？
9. 是否具备可自动化验证的 DoD，以及必要的真机验收清单？
10. 如果不做，真实使用是否仍然顺畅？

只有前四项有明确正收益，且后续风险可控，才值得进入排期。
